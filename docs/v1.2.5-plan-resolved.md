## 3. 剩余主线：Bug B —— 封装 I/O 重排后外部连线不跟随（✅ 已解决，v1.2.4）

> **✅ 已解决**：本节 Bug B 由 v1.2.4 稳定 pinId 重构（commit `ebe470f`，即 §3.3 的「方案 3」）彻底解决。以下历史分析保留作存档，代码现状核对见 §3.5。

### 3.1 现状确认（当前上游代码）

- 引脚顺序仍由 Y 排序决定：`GraphNode.getSubNodes`（`GraphNode.java:112-116`）按 Y 升序、Y 相同再按 id 决胜。
- 外部连线 `NodeConnection` 仍只存整数 `fromPin`/`toPin` 索引，无名字 / 无 pinId。
- 移动 I/O 节点只发 `MOVE_NODE` 改 Y，全仓**无任何「重排后重编号连线」逻辑**。
- 结论：Bug B 根因未变，仍需修。详见 `encap-io-bugs.md` §0、§B。

### 3.2 推荐方案：方案 2（重排时重编号 / 重连外部连线）

保留现有「移动 I/O 节点 = 重排对外引脚」的 UX（设计本意：引脚顺序跟随内部视觉布局，`GraphNode.java:107-111` 注释），但在移动**落定**时把连线索引一起置换，使线跟随节点走。

具体步骤：

1. **新增连线换向能力**
   - 在 `OpType` 增加 `REWIRE`（或在 `NodeGraph`/数据包层用 `REMOVE_CONN`+`ADD_CONN` 配对）。
   - 在 `OpExecutor`、`GraphEditOpPacket`（及客户端 `onRemoteOp`）实现：更新一条已有 `NodeConnection` 的 `fromPin`/`toPin`（连线本身不携带额外数据，remove+add 等价且安全）。
2. **在 MOVE_NODE 落定处触发重连**
   - 定位当前拖拽结束分支（搜索 `OpType.MOVE_NODE` 落定逻辑；旧文档指 `:2609` 已因上游 +1140 行重构而过时，需重新定位）。
   - 若被移动的节点是 `ENCAP_INPUT` / `ENCAP_OUTPUT`，且其在兄弟中的 Y 排序位置发生变化：  
     a. 计算移动前 / 后的「旧索引 → 新索引」置换（分别对 INPUT 组、OUTPUT 组）；  
     b. 遍历**父图**的 `NodeConnection`：凡 `toId == encapId` 的 `toPin`、`fromId == encapId` 的 `fromPin`，经置换得到新引脚，发出 `REWIRE`；  
     c. **嵌套处理**：若本封装自身是外层封装的 I/O，则外层连到本封装的连线也需同样置换 —— 循环向上直至顶层图。
3. **撤销支持**
   - `REWIRE` 记录旧引脚，纳入撤销栈（与现有 op 撤销机制一致）。

行数估算：约 **90–130 行**（重连 helper ~50–80 行 + `OpType`/`OpExecutor`/序列化 ~30–50 行）。比信号发生器/探针（+3971/-50）小一个数量级。

### 3.3 备选方案

- **方案 1（pinOrder 字段）**：给 `ENCAP_INPUT/OUTPUT` 增加显式 `pinOrder`，`getSubNodes` 按 `pinOrder` 排序，移动不再改变引脚顺序，需额外「显式重排」UI（右键上移/下移）。更「干净」但改变 UX，且重排时**仍需重连** → 不比方案 2 省事。约 80–120 行 + 重排 UI。
- **方案 3（稳定 pinId）**：连线绑定不可变 `pinId`，移动/插入/删除都不串线，最彻底；但需改 `NodeConnection` 结构与序列化、求值器/渲染全适配 `pinId`，约 200–260 行，属较大重构。建议作为**长期方向**，不在 v1.2.5 必做。

  > **关联**：方案 3 同样会解决 [`formula-pin-render-tech-debt.md`](./formula-pin-render-tech-debt.md) 中 FORMULA 节点的引脚变更后连线不显示问题。FORMULA 的 `dynamicInputCount` 变化本质上是引脚被插入/删除，与 ENCAP I/O 的引脚重排共享同一根因——连线用整数索引绑定，引脚集合变化时索引失效。方案 3 一次性解决全部。

> 推荐先落地方案 2（最小正确修复、保留现有 UX），把方案 3 列为后续健壮性重构。

### 3.4 验证

- 复现 `encap-io-bugs.md` §B 步骤应变为：把 B 拖到 A 上方后，**线 a 跟随 A 到槽1、线 b 跟随 B 到槽0**，数据流不翻转。
- 兼容性：已保存原理图（MOVE 已持久化旧排序）加载后连线仍按存储索引解释，无回归；多人协同下 `REWIRE` 经服务端权威广播生效。

### 3.5 现状核对（2026-08-01）—— 方案 3 已落地，Bug B 已修复

代码验证结论（与 §3.1「现状确认」逐条对照）：

- **稳定 pinId 绑定**：`NodeConnection` 增加 `fromPinId`/`toPinId` 字段，整数 `fromPin`/`toPin` 降级为派生的缓存索引。ENCAP 的 `pinId = String.valueOf(subNode.id)`（`GraphNode.java` `inputPinId`/`outputPinId` 第 261–264 / 292–295 行），子节点 ID 在拖动重排（MOVE_NODE 只改 Y）时不变。
- **重排后自动重解析**：`NodeGraph.rebuildInputCache()` 在每次拓扑变化（`invalidateTopo`）时把 pinId 重新解析为当前整数索引，并剪除已失效连接（`NodeGraph.java:193-222`）。拖 I/O 节点改 Y → 外部连线经 pinId 找到新槽位，数据流不翻转。
- **求值按 pinId 注入**：`GraphEvaluator` ENCAP 分支构建「pinId → 值」映射注入 `ENCAP_INPUT`（`GraphEvaluator.java:916-933`），不依赖缓存位置。
- **旧存档迁移**：`GraphMigration.migrateV3toV4`（`NbtVersions.DATA_VERSION` 3→4）把整数索引连接转换为 pinId，重排/改名不串线。

> 结论：§3.1 所列根因（连线只存整数索引）已消除。V4 存档加载后按 pinId 解释连线；新建连线也直接携带 pinId。§3.2 推荐的「方案 2 REWIRE」无需实施——方案 3 从根因上解决，并同时覆盖 FORMULA 引脚增删（见 `formula-pin-render-tech-debt.md` 关联说明）。
