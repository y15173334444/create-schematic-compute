## 一、问题与已有结论 / Problem and Prior Conclusions

### 1.1 现象

跨**方块实体**的通道信号（`BUS_IN/OUT`、`PRIVATE_IN/OUT`）在本 tick 是否可见，
取决于"谁先 tick"；而 BE tick 顺序由原版决定（区块内方块实体表迭代序 + 中途新增走 pending 表），
模组无法控制、且会随区块重载翻转变动。

### 1.2 机制证据（2026-09-11 核对，2026-09-30 去锚点重述）

| 环节 | 落点（机制） | 时机 |
| --- | --- | --- |
| PRIVATE 读 / 写 | 求值器的私有信号读分支 / 写分支 | 求值过程中（**惰性读，非快照；就地写**） |
| BUS 读 / 写 | 求值器的总线读分支 / 写分支 | 求值过程中（就地） |
| 红石输出落地 | 宿主求值后的输出写出（写回红石链接网络） | 求值调用返回**之后** |
| 服务端 tick 前钩子 | 模组入口的 `ServerTickEvent.Pre` | 只复位 FORMULA 预算 |
| 服务端 tick 后钩子 | 模组入口的 `ServerTickEvent.Post` | 只做 blob 清理 |
| 十个宿主的求值体 | 十个方块实体各一份（蓝图 / 程序计算机 / 转速代理 / 显示器 / 数控齿轮箱 / 传感器 / 可变速器 / 控制椅 / 雷达 / 动力仪表） | 全部**无间隔** ticker。⚠️ 旧稿记 9 个，**动力仪表未计入**，本轮更正（§附录 C） |

**全仓没有 tick 末二次求值、没有传播队列、没有主机排序。**【核实】

### 1.3 原版时序证据（反编译源码实测，非推断）【核实】

服务端一个 tick 的顺序：**方块刻（含计划刻）→ 流体刻 → 袭击 → 区块刻 → 实体刻 → 方块实体刻**；
服务端 tick 前 / 后事件分别包住整段（`Pre` → 整个 level tick → `Post`）。
**当前求值位置 = 方块实体刻。**

**两条推论**：

1. **方块刻本来就排在方块实体刻之前** → 把求值整段挪到 `Post`，对**方块刻消费者**（方块 / 机械）的消费时机**毫无影响**（两种情况下都要等下一 tick 的方块刻）。
2. 但方块实体刻是**一个循环** → 同一 tick 内**排在后面的 BE 能读到前面 BE 刚写的值**。把求值挪到 `Post`（在该循环之后）会**整体关闭这个"同 tick 拾取窗口"**，影响两类消费者：
    - 本模组的 Kinetic 系宿主（可变速器 / 数控齿轮箱）
    - Create 自己的动力件（离合器 / 变速箱读红石功率）

> ⚠️ 本文档早期版本写的"方案 A 违反 G4（外部可见输出 +1 tick）"**只对方块刻成立，对 BE 介质不成立**，已在 §附录 C 记录更正。

### 1.4 准确措辞

**不是"读到缓存旧值"**——进程内总线是实时表，读到的永远是**当前时刻**的值。
问题是**上游可能本 tick 还没跑到**：

```
BE_A.tick() [写 ch=7]        BE_B.tick() [读 ch → 7]     ✅ 同 tick
BE_B.tick() [读 ch → T-1 值]  BE_A.tick() [写 ch=7]      ❌ 1 tick
```

即跨 BE 是 **0 或 1 tick，不确定**。对 PID / 火控而言，**抖动延迟不可建模补偿，固定延迟可以**。

### 设计原则

- **P1｜内联门控优先于中央队列**：公式节点预算池之所以是"内联门控、拓扑位就地求值"而非"预算分配的中央队列"，就是因为多余的 1 tick 对**火控预判**影响大。
  → **任何为简化而引入 tick 级延迟的方案默认否决**；推论：环上被切的边必须切在**火控非关键路径**（见 §5.3）。
- **P2｜通道治理边界**：Create 无线红石网络的时序归 Create 所有，**既不改也不测**（只作为"外部常量延迟"在文档中提及）。

## 三、C 阶段方案：观测设施 / Phase C: Observation Facility

### 3.1 判定规则（口径 A）

```
写入侧：PRIVATE_OUT / BUS_OUT 分支 → channelEpoch.bump(key)
读取侧：PRIVATE_IN / BUS_IN  分支 → 记录 (key, epoch, value)
Post  ：对每条记录，若 channelEpoch.get(key) > 记录时的 epoch → ① 陈旧读
        再比较 channelEpoch 对应通道的当前值 vs 记录时的 value → ② 陈旧且值不同
```

- 额外零成本收益：**陈旧跨度**（同 tick 内被超越 / 跨 tick）
- **传递闭包**：拿到标记集合后，沿 BE 级依赖图向下游传播"受影响"标记 —— **不重算**即可给出受影响范围，这是影子重算的一阶近似，只要 O(边数)
- **局限（诚实记录）**：它测的是"读者的**输入**是旧的"，不是"读者的**输出**必然不同"。② 档用值对比滤掉一阶误报，但多跳传播中"值恰好抵消"的情况它看不出来（那需要口径 B 影子重算，留作复现问题时的临时开关）

### 3.2 范围

| 项 | 纳入 | 理由 |
| --- | --- | --- |
| BUS（进程内总线通道） | ✅ | 进程内、模组自持、可被调度器影响 |
| PRIVATE（进程内私有信号） | ✅ | 同上 |
| Create 红石链接 | ❌ | **P2**：它是**互操作兜底通道**（与原版红石 / 他人模组对话），**不是本模组跨机通信的主力**（主力是 BUS / PRIVATE）→ 时序归 Create，既不测也不改；读侧还是"tick 开头整网快照"，epoch 模型也不适用 |
| host 范围 | 只统计本 tick 实际求值者（`running && graph.nodes` 非空） | 停机 host 既不读也不写，纳入只会稀释分母 |
| **ENCAP 封装子图** | ✅ **必须递归** | 已核实：封装求值走**同一个 eval switch**，所以子图里的 `BUS_OUT`/`PRIVATE_OUT` 一样写全局总线。不递归则 BE 级 DAG 不完整，观测与将来切边全错（ENCAP 套 ENCAP 需再递归） |
| SCC 环检测 | ✅ | 结构信息几乎白送；是切边策略的**唯一**前置 |

**顺带推论**：同一个 host 内部，主图与 ENCAP 子图可能写 / 读同一通道 → **通道边（含 host 自环）也要进 DAG**，不能只算跨 host 边。

### 3.3 采集点（**关键实现选择**）

记录点应放在 **求值器的 `BUS_IN` / `PRIVATE_IN` 分支**（那里正是读通道处），而不是散落到 10 个 BE 的 tick 体里。但收集器需要知道"当前是哪个 host"，而求值器只持有图、不持有 host（子 evaluator 更是如此）。

**两个可选实现**：

1. **静态 per-tick 收集器 + 当前 host 上下文**（推荐）：求值是**单线程服务端**，用一个静态 `TopoStats.currentHost` + 收集表即可；子 evaluator 通过同一静态天然延续，无需改求值的 4 个重载。**代价**：需在 10 个 BE 的求值处设 / 清上下文。
2. **给求值入口加 `StatsSink` 参数**：显式、无静态状态，但要改签名 + 10 处调用点 + 子图透传。

**无论哪种，都建议先做 §6.3 的"10 份 tick 体收敛进 `GraphHost`"** —— 收敛后钩子只有**一处**，否则要在 10 处设 / 清上下文（或写 10 个 wrapper）。这使 §6.3 从"顺带收益"升级为 **C 的 hook 点前置**。

### 3.4 全局注册表 + Post 汇总

- **全局 host 注册表**（本期建）：`load` / `onLoad` / `onChunkUnloaded` / `setRemoved` 生命周期钩子增删；`GraphHost` 已有 NBT 存取与 BUS 生命周期钩子可挂靠
- **跨维度**：进程内总线是**进程级静态表**，**无维度作用域**。注册表与 DAG 必须同样跨维度建（否则跨维度链失效）
- **Post 汇总**：`ServerTickEvent.Post`（模组入口的既有钩子）里做 epoch 对比 + 统计落盘；**不改变求值时序**

### 3.5 判读标准（观测完怎么决策）

| 观测结果 | 结论 |
| --- | --- |
| ② 长期为 0 | "顺序反了也不影响值" → (A) 与 (B) 实际等价 → **选 (A)（最简）** |
| ② 频繁，且分布在不同 host | (B) 的补跑确有价值，`stale`/`topo` 会直接指出是哪些通道、哪些 host |
| `ring` 报出 SCC | 无论 ② 如何，**环必须切边**（见 §5.3）——这是唯一"无论如何都要处理"的情况 |

## 四、C 阶段方案：图内 `/` 悬浮控制台 / Phase C: In-Editor "/" Console

### 4.1 落地形态（Q6 = A）

- **控制台本体独立成文件**：`client/GraphConsole.java`（状态 + 渲染 + 输入 + 命令解析）
- **共享编辑器只加约 5 行**：
    1. `/` 键 → 切换可见性（`GLFW_KEY_SLASH` 全仓无绑定 ✓）
    2. `keyPressed` 守卫链**链首**加一条
    3. `charTyped` 守卫链链首加一条
    4. `render()` 里一次 `console.render(g, mouseX, mouseY, partialTick)`
- **收益**：编辑器是共享画布 → 控制台天然覆盖 **7 个编辑器 + 便携终端**；图保持实时（探针趋势图 / `clientTick()` 不中断）
- **与既有 GUI 重构的关系**：原"并行拆解、rebase 5 行"的前提**已消失**（§6.1 二次修订）。现在的事实是"往全仓最大、改动最频繁的文件插 5 行"：插入点（按键 / 字符输入守卫链、`render`）在 `GraphEditor` 里**仍然有效**，因为 6f 后半（`renderBg` / `keyPressed`）明确延后、未分解。代价换成另一面：**未来若做 6f 后半或 IDE 重构，这 5 行要跟着搬**（§6.2 / §9.5-4）。

### 4.2 输入隔离

- 守卫链既有顺序：导出命名框 → 取色器 → 顶栏命名框 → 各节点编辑框 → 全局快捷键
- 控制台是**最新 / 最上层的叠加层** → 插在**链首**
- **ESC 语义**：控制台打开时 ESC 应**关闭控制台**而非整个编辑器（须在链首拦截，避免走到 Screen 默认 `onClose`）
- 打开控制台时清掉其他 EditBox 焦点（避免双焦点）
- 先例：取色器 / 导出对话框已是同类叠加层，模式**已有**，不是新范式

### 4.3 命令集（全部只读）

| 命令 | 输出 | 服务目标 |
| --- | --- | --- |
| `help` | 命令列表（**由服务端返回**，客户端不硬编码文法） | REPL 必需 |
| `stale` | 本 host ①/② 次数，按通道分组 + 跨度 | **口径 A 核心数据** |
| `topo` | 本 host 读写集 + 上游 / 下游 host（坐标 + 通道名） | 定位"谁在拖后腿" |
| `ring` | 全局 BE 级依赖图的 SCC 列表（环成员 + 环上通道名） | **切边唯一输入** |
| `bus` | 本 host 通道：名 / 当前值 / owner / 订阅者数 / 总线冲突标记 | 给现有 BUS 冲突机制一个界面（目前只能靠日志） |
| `perf` | **求值耗时（⚠️ 当前无埋点，需新增 `nanoTime` 包夹）**、公式预算余量 / slice、**去重命中与未命中**、重公式数上期值 | 给几个**零消费者的孤儿访问器**接上消费者；并补上缺失的耗时埋点（见 §8.5 与 §9.2-1） |
| `hosts` | 全局 host 清单（坐标 / running / 本 tick 求值序号 / 陈旧计数） | 判读 `stale` 必需的上下文 |

**不做（第一期）**：任何**写**操作（`set`/`run`/`edit`/`toggle` —— 涉及多人协作、op 权限、撤销栈、回滚，而 C 阶段只需观测）；节点定点采样（`probe <nodeId>`）；自动补全（需客户端持有文法，与"服务端唯一真相源"冲突）。

### 4.4 协议与权限

**推荐**：客户端把**原始字符串**发给服务端，服务端解析（`help`/文法全在服务端）→ 回文本行。

- 理由：客户端零文法 = 单一真相源；命令集演进不需要改客户端
- **新增一对包**：`ConsoleQueryPacket`(C→S, `BlockPos` + `String`) / `ConsoleResponsePacket`(S→C, 文本行列表 + 行数上限)
- **距离校验**：本 host 查询复用既有的可达距离校验惯例（10+ 包在用）

#### 权限模型：**不限 OP**，改分层缓解（2026-09-11 决策）

**威胁模型（已核实，非推测）**：这不是 DDoS（单个玩家即可），而是**主线程包洪泛 + 响应放大**。

- 原版只对聊天 / 命令类节流（`detectRateSpam`，≈10 次 / 秒），且只在少数入口调用
- **自定义负载完全无限流**：原版只是把自定义负载转发给你的处理器
- **本仓库现状**：10+ 个 C→S 包**全部只做距离校验，无任何服务端限流**；代码中的 `throttle` 全在**客户端发送侧** → **客户端节流挡不住被改过的客户端**
- **放大系数**：`hosts`/`ring` 响应为 O(全部 host)；小请求换服务端主线程 CPU + 出站带宽（响应只发给请求者，故表现为"拖慢服务器"而非打别人）
- ⚠️ **既有缺口（非本功能引入）**：图编辑 op 包一个 op 会被**广播给所有编辑者**，广播放大系数高于控制台查询 —— 限流设施的价值不止于控制台

**分层缓解（按性价比）**：

| # | 措施 | 效果 |
| --- | --- | --- |
| 1 | **服务端限流**（per-player + per-packet-type 令牌桶；语义照原版：允许突发、持续超限则**断开**） | 补上**全部** C→S 包都缺的一块；建议做成可复用小工具，控制台只是第一个受益者 |
| 2 | **全局查询脏缓存**（`ring`/`hosts` 每 N tick 最多重算一次，请求从缓存复制） | **消掉放大系数**：O(hosts) → O(1) 摊还，收益最大 |
| 3 | **响应上限 + 截断**（行数 / 字节硬上界，超出显示 `…(+N more)`） | 单次请求成本有上界 |
| 4 | 距离校验沿用惯例 | 挡住远程探测任意方块 |
| 5 | ~~限 OP~~ | **有了 1-3 即不必要**；若要更保守，可只在单人 / 局域网放开全局命令 |

**推论**：限流设施（第 1 项）应作为**独立的安全修复提交**，独立于本观测功能；它同时降低既有编辑 op 包的暴露面。

- 仍待确认：① 原始字符串 vs 结构化请求；② 响应上限具体值（建议 200 行 / 8KB）；③ 超限行为（丢弃 + 回一行提示，还是照原版语义断开）

## 五、后续（决策 (A)/(B)/切边）的设计预案 / Follow-up Designs: (A)/(B)/Edge Cutting

> 本节**不在 C 阶段实施**，仅为观测结论出来后的决策预留设计，避免返工。

### 5.1 语义不变量

| 编号 | 语义 |
| --- | --- |
| S1 | 同一 BE 内：单遍拓扑序，读写严格有序（**已满足**） |
| S2 | 跨 BE、无环：本 tick 末所有 host 的值 = 按 BE 依赖拓扑序的**不动点** |
| S3 | 跨 BE、有环：环上切一条边 → 被切边跨 tick（恒定 1 tick），环外仍满足 S2 |
| S4 | 未加载 / 未注册的 writer：视为"无写者"，读取保持总线现状，不阻塞不报错 |
| S5 | FORMULA 挂起中：输出保持冻结（emit-on-done），补跑不得打破 |
| S6 | 广播：每 host 每 tick **只广播最终值一次** |

### 5.2 (A) 单通道 vs (B) 保留首跑 + 补跑（修正版对比）

| 方案 | 值的确定性 | 物理生效时机 | CPU | 机制复杂度 |
| --- | --- | --- | --- | --- |
| **(A) 全部求值移到 Post，一遍 host 级拓扑** | 确定 | **uniform 1 tick**（同 tick 拾取窗口关闭） | 1× 求值 | 低（无 epoch、无补跑） |
| **(B) BE 首跑 + Post 拓扑补跑收敛** | 确定 | **0 或 1 tick 抖动**（保留窗口） | 1× + 补跑 | 中（epoch + 反向索引 + 上限） |

**判读**：P1 说"1 tick 影响火控预判"，但火控同样怕**抖动**。→ 这正是 §3.5 要用 ② 档数据来定的原因：**② 为 0 说明抖动无害，选 (A)；② 频繁说明抖动真实存在，(B) 的保窗口才有意义**。

### 5.3 环处理（SCC + 确定性切边）

- BE 级依赖图检测到环 → **切一条边**使跨 tick
- **切边规则待定**，但受 **P1 约束**：必须切在**火控非关键路径**上。候选：
    - (a) 稳定哈希最小边（确定性，但可能切到关键路径）
    - (b) 坐标字典序（同上）
    - (c) **显式声明**：给 `BUS_OUT` 加 feedback 标记，由用户在编辑器里声明哪条边跨 tick ← **与 P1 最一致**
- 我的倾向：**(c) 为语义正确路径 + (a) 作兜底**（未声明时自动切），并把切边结果在编辑器可视化（可并入控制台的 `ring` 输出）

### 5.4 不要合并节点图（分析结论）

跨 BE 边**只有通道边** → 把每个 host 的节点图拓扑序**投影到 host 上**即等价于合并图的拓扑序。真合并节点图会撞四堵墙：

1. **节点 id 命名空间冲突**（最狠）：PID 状态以节点 id 为键，而 id 是**每图各自分配**的整数 → 合并后不同 host 节点 id 撞车，PID 积分互相污染
2. 每 host 的运行时状态（PID / 延时队列 / 触发器 / 脉冲计时 / 边沿标记 / 调试相位 / 子图状态）
3. 每 host 的 evaluator 与输入源（编码器视图 / 雷达坐标定制注入、红石链接、座椅输入）
4. NBT 归属 + 每 BE 协作编辑会话（`EditSessionRegistry`）

→ **按 host 收集 + host 级拓扑**，不要按 node 合并。

### 5.5 FORMULA 预算池的基准问题（**结论已修正，见 §附录 C**）

公式预算池在**服务端 tick 前钩子**里建立 deadline：`deadline = now + 预算`；
"是否过期"的判定即 `nanoTime() >= deadline`。

**旧稿推论**：Pre→Post 之间隔着实体刻、区块刻、网络，通常远超 3ms 预算 → 若把求值挪到 Post，必须把**基准改到求值段开始时**（去重表清空一并挪过去），否则循环型 FORMULA 的进度会被压到"每边界 16 次迭代"就挂起。

> ⚠️ **2026-09-30 修正**：本轮核实——**该 deadline 判定没有任何调用点**（既不是被解释器入口检查，也不被求值器检查）。也就是说当前**没有**"每 tick 总预算兜底"这个机制，只有"循环边界按片让出"（见 §9.2-1）。
> **因此**：§5.5 的基准搬迁需求**只有在先接上兜底之后**才成立；在此之前，"把求值挪到 Post"不受此约束，但同样也**得不到**兜底保护。接上兜底的那次提交必须同时做基准搬迁，否则会把循环型脚本压到几乎不前进。

### 5.6 环会让 naive 全局拓扑"静默炸"（重要发现）

图内拓扑排序是标准 Kahn：**只把入度归零的节点放进有序表**，而求值**只遍历有序表** → **环内节点根本不求值，保留旧值**。

图内环编辑器有检测（README 🛡️ Cycle Detection），但**跨 BE 通道环（A→B→A）它看不见**。全局拓扑一旦遇到这种环：**整条环上的 host 静默停更**——比现状的 1 tick 糟得多，且极难排查。→ 这就是为什么环必须显式 SCC + 切边（§5.3），而不是"交给拓扑排序顺手处理"。

## 七、立项选型：为什么是图形化节点编程，而不是红石方块式方案 / Why a Node-Graph Mod, Not a Block-Per-Function Redstone Design

> **本节回答立项问题** —— 它不是性能对比的附属品。判据与结论在 7.1–7.10；
> 对照方案的机制细节与逐条源码核对在 §7.11；本模组自身的性能基线、埋点与优化项在 §八。
> **诚信前提**：对照方案确实更好的地方**单列在 §7.9**，不藏在正文缝里。

### 7.1 立项要做的三类功能

按难度递进 —— 这三类里能做到哪一类，直接决定选型：

| # | 目标用例 | 需要的能力 |
| --- | --- | --- |
| ① | 单轴 / 8 轴 PID 姿态控制 | 加减、常数加权、PID、限幅、时序整形（延时 / 锁存 / 触发器 / 脉冲） |
| ② | 8 轴 + 交叉耦合（姿态耦合矩阵） | **信号 × 信号**（矩阵乘法） |
| ③ | 姿态解算 / 弹道反解火控 | 乘法、三角、开方、条件、**循环迭代**、可装载的脚本（§8.6 有一份 192 行的实测脚本） |

### 7.2 两条候选路径，与五条判据

| 路径 | "程序"写在哪 | 连接方式 | 计算位置 | 状态位置 |
| --- | --- | --- | --- | --- |
| **方块式方案** | 世界坐标（一片装置） | 方块面 + 邻居通知（物理连线） | 每个方块自己的方块刻 | 每个方块实体自己的字段 / NBT |
| **图形化节点编程**（本模组） | 一个方块实体内（节点图 / 公式） | 编辑器里连线（进程内） | 该方块实体每 tick 一遍图 | 该方块实体的运行时状态 |

一句话差别：**方块式方案把程序摊进世界坐标，节点编程把程序收进一个方块实体。**

五条判据（按立项时的权重排序）：

1. **表达力上限** —— 这类功能**能不能**表达（不是快不快）；
2. **规模密度** —— 同一功能要占多少世界资源；
3. **世界机制成本** —— 是否争夺原版 / Create 的共享资源，**放大系数是否可控**；
4. **迭代与调试成本** —— 改一个参数、复现一个 bug 要动多少东西；
5. **精度与延迟** —— 控制回路最关心的两个数（**红石通道吃亏、动力通道不吃亏**，见 §7.6）。

### 7.3 判据①：表达力 —— 对方的能力边界正好挡在第 ② 类用例上

对照方案可表达的：加减（符号固定）、常数加权求和、PID（多级 I/D）、PWM 抖动输出、阈值 / 过零检测、
位打包总线。**不可表达**：两个信号相乘、除法、三角 / 开方 / log、循环迭代、用户脚本、
任意布尔组合、对"活信号"的比较（只能与常量比）、显式寄存器 / 计数器。

| 用例 | 方块式方案 | 结论 |
| --- | --- | --- |
| ① 8 轴 PID | 可表达（16–32 方块，§7.4） | **这条判据在这里还分不出胜负** |
| ② 交叉耦合矩阵 | **不可表达**（矩阵乘法） | 只有节点编程 |
| ③ 解算 / 反解 | **不可表达**（无循环、无脚本） | 只有节点编程 |

→ **立项时就已确定：要覆盖 ②③，只有节点编程这一条路径。这是选型的第一因，不是"性能更好"。**
→ **代价**：我们因此背了一个公式解释器 + 图编译 + 图编辑器 —— 全仓 45,326 行 Java 的主因，
维护面远大于"31 个方块类"（§7.9、§7.10）。

### 7.4 判据②③：规模密度与压力对照（按功能换算 + 两个正确配对）

> 先纠正一个容易走偏的比法：**方块 = 固定功能，节点 = 单个运算**；1024 节点是**容量上限**不是实际用量。
> 所以下面先按功能换算，再给出两个**对等**的配对。


**场景 A｜本模组**：20 台计算机（各满载 1024 节点）+ 每台被 10 名玩家追踪 + 其中 1 台跑
**100 万次迭代的火控公式**（预算池默认 3.0 ms/tick）。

| 项 | 数值 | 来源 |
| --- | --- | --- |
| 求值（无预算，线性无界） | 20 × 0.15 ms = **3.0 ms/tick** | §8.2 |
| 公式（预算池上界） | ≤ 预算档 = **3.0 ms/tick**（`slice = 预算 / max(1, 重公式数)`，保底零饿死） | 预算池实现 |

| **解算延迟** | **~200–230k 仿真步 / 解算 → 150–200 ms → 默认 3 ms/tick 下 ≈ 50–65 tick ≈ 2.5–3.3 s**（§8.6 按真实脚本重算；原估 20 tick / 1 s 偏乐观） | 见 §8.6 |

| 峰值（单台解算） | ≈ **3.2 MB/tick ≈ 64 MB/s** | — |

> ⚠️ **两条关键耦合**（原文档未记录）：
> 1. **单次解算的迭代上限不只是"防病态循环"，它同时等于"单次解算最多产生 ~24 MB 垃圾"**。火控若真按 100 万迭代设计，就**贴在上限上**——再多一次迭代即硬 shed 到 `lastGood`。建议火控目标留在 30–60 万迭代（文档示例即 ~60 万）。
> 2. **预算池把"主线程成本"变成硬上界，代价是"解算时延"**：3 ms/tick 下，按真实脚本重算约 **2.5–3.3 s 的滞后解**（§8.6），且**时延 ∝ 同时解算的重公式数**（预算总量固定）。
>    对移动目标即"解算完成时目标已移走"——需靠 warm 续算、**热启动（§8.6 优化 1）**、或显式补偿。**这是设计取舍，不是 bug。**

**场景 B｜方块式方案**：8 轴完整链路（万向节输入 4–8 + PID 8 + 混合 8 + 输出 4–8 ≈ **32 方块**）。

| --- | --- | --- |

> ⚠️ **配对修正（2026-09-11）**：场景 A 与场景 B **不是对等物**，不能并排下"对称结论"。
> A 是"20 台满载 + 火控"（极端服务器负载），B 是"1 套典型 8 轴飞控（~32 方块）"。

> **不要用"32 方块 vs 1024 节点"配对。**

**按功能的资源换算（估算）**

| --- | --- | --- | --- |

**由此得到两个正确配对**

| 配对 | 本模组 | 方块式方案 | 主线程 | 世界触发 | GC |
| --- | --- | --- | --- | --- | --- |
| **① 典型单机（8 轴飞控）** | 1 台 × ~60 节点 | ~32 方块 | 本方 ~**9 µs** vs 对方 ≈ 0 | 本方 **0** vs 对方 **96 次/tick**（+ 级联） | 本方 ~**5.8 KB/tick** vs 对方 ~24 KB/tick |
| **② 极端服务器** | 20 台 × 1024 节点 + 火控 | **无对等物** | 本方 ~6 ms/tick | — | 本方峰值 ~520 MB/s（公式装箱主导） |

> **结论修正**：在**典型单机规模**下，本模组的主线程与 GC **都优于方块式方案**；对方剩下的优势只有"链式 0 tick 延迟 + 亚级输出"，代价是 **~96 次世界机制触发/tick 且会级联**。本模组的劣势要到配对②（满载 × 多台）才出现——而那时对方**已无对等物可比**（遇到乘法即终止）。
> ⚠️ 但"链式 0 tick"这条优势**需要打折**：见 §7.11-3，对方的同 tick 收敛在**汇聚扇入**处同样不成立。

> **第一优先因此改变**：服务器规模下，**eval 侧（H×N 线性无界）先撞线，早于 §8.4 的广播**。
> §8.3 的双克隆与"eval 预算 / 输入指纹短路"应优先于广播节流。

### 7.5 判据③：世界机制成本 —— 触发次数与级联放大

> 这一条问的不是"谁算得快"，而是"**谁在争抢全服共享的资源，且放大系数由谁控制**"。


> **术语校正**：立项时所说的"红石内存泄漏"，实指 **allocation churn / GC 压迫**——
> 对象**可达**（非 leak），但**分配速率过高 → 新生代收集频繁 → JVM 停顿卡顿**。
> 这决定了测法：看 **bytes/tick 与停顿**，不看堆占用曲线。

**每单位每 tick 的分配清单（静态，2026-09-30 按对照方案源码复核）**

| | 方块式方案（每常开方块） | 本模组（每节点） |
| --- | --- | --- |
| 数组 | 每次求值 `new int[6]`（六面输入）+ 部分方块再加 `new int[6]`（输出） | 输出数组克隆 **×2**（双克隆，§8.3） |
| 为"读值"而分配 | PID 系每次求值 `new double[级数]` ×2（积分链 / 微分链） | — |
| 装箱 | — | 输出表 `Integer`、输入缓存 `Long` |
| **世界机制触发** | **每次输出变化**：1 次邻居通知扇出（= **6 次 `neighborChanged`**，其中每个方块式邻居都会再排一个 **0 延迟计划刻**）+ 1 次方块更新包 | 无 |
| 包 | 每次输出变化 → **每追踪玩家一个方块更新包** | 每 tick 一份全图快照 + 一个包 **× 追踪玩家** |

> **计数口径更正（2026-09-30）**：旧稿写的"12 次 `updateNeighborsAt`"是把"6 次邻居通知"与两条触发路径重复计数的口径错误。按对照方案源码逐条核对：**每次输出变化 = 1 次邻居通知扇出（6 次 `neighborChanged`）+ 6 个 0 延迟计划刻插入 + 1 次方块更新包**。量级结论不变（每方块每次变化仍是 6–12 次世界机制入口），已记入 §附录 C。

**量级换算（估算）**

| | 规模 | 对象 / tick | 字节 / 秒 | 世界机制触发 / tick |
| --- | --- | --- | --- | --- |
| 方块式方案 | 8 通道（8 常开方块） | ~240 | ~0.15 MB/s | **48 次邻居通知 + 48 个计划刻插入**（8 × 6，值变化时） |
| 本模组 | 满载（1024 节点） | ~4k | ~3 MB/s | **1 次发包 × 玩家** |

**两个结论**

1. **两边模组自身的分配速率都远低于 G1 的门槛**（G1 面向几百 MB/s–GB/s；3 MB/s 是零头）→ **"模组 new 太多"不是痛点的来源**。
2. 真正的差别是**世界机制触发次数**：方块式方案 8 通道每次值变化 **48 次邻居通知 + 48 个计划刻插入**（入队 + 分层展开 + 每变化每人一个包），本模组是 **1 次发包**。**降的是触发次数与共享放大，不是 new 的次数。**

> 原版红石的 GC / 卡顿痛感来自三件事叠加（**本段为推断，未逐一验证**）：
> ① 规模（装置方块数 × 每 tick 更新次数）；
> ② 共享放大（一次更新触发邻居 `neighborChanged`，其中再触发更新 → 分层展开）；
> ③ **retained 增长**（每区块调度集、方块事件、方块实体表、区块重渲染 / 形状缓存）
> —— ③ 才是"堆真的变大"，而它随**装置规模**增长，**不随分配速率**。

**立项叙事因此成立**：把 8 路 PID 从"8 方块 × 每 tick 6–12 次邻居通知"压成"1 方块 × 内部求值 + 1 个包"，
**世界机制触发降低 1–2 个数量级**；代价转移到自包含的年轻代短命对象——可控、可测、不影响他人。

### 7.6 判据⑤：精度与延迟 —— 亏在红石通道，动力通道不吃亏

| 项 | 方块式方案 | 本模组 |
| --- | --- | --- |
| 链式传播延迟 | **同 tick**（递归直调；⚠️ 汇聚扇入处打折 §7.11-3；**对外通信仍 1 tick**，§7.9-1） | **0 或 1 tick 不确定**（§一） |
| 跨计算机通信 | 方块面 + 邻居通知（落在世界的红石语义上，整数） | **进程内总线 / 私有信号：float32、按名寻址、不占世界方块与邻居机制**；红石链接只作兜底（§7.8） |
| 出口通道 | 红石 0–15（唯一出口）+ 方块内部抖动给出的**亚级** | 红石 0–15（**无抖动**）+ **动力通道 ±256 RPM**（Create 原生接口，浮点读回） |
| 内部数值 | 整数总线（[-15,15]，4 bit 幅值 + 符号打包） | **float32** |
| 反馈频率与空闲 | 20 Hz，但求值挂在**共享计划刻队列**上（§7.9-1） | **20 Hz 硬上限**；每 tick 遍历图，但**完成且输入未变的公式节点整节点跳过**（§7.9-3） |

- **亏的一条**：**红石通道**没有抖动 / 亚级（§9.3-1）—— 加一个"抖动输出"节点即可补；**动力通道不缺精度**（±256 RPM）。
- **赚的两条**：内部 float32 + 图 + 公式，使第 ②③ 类用例的中间量不丢精度；动力通道直接给 ±256 RPM，比红石 0–15 宽两个数量级。
- **立项取舍**：**把红石通道的精度让给后续打补丁，把表达力在立项时一次锁死** —— 精度能补，表达力不能。

### 7.8 状态、持久化与可携带性

- **持久化**：本模组的运行时状态（PID / 延时队列 / 锁存 / 脉冲 / 公式载体）随 NBT 完整存取；
  对照方案只存 PID 与配置，**纯传递方块的输出、抖动累加器、上一拍输入都不存**（区块重载后归零，
  直到下一次输入变化），双轴方块的第二轴状态还与第一轴共用同一组 NBT 键（§7.11-4）。
- **跨区块 / 跨维度**：单方块只依赖自己所在区块；一片装置要整体保持在加载范围内，少一块就断链。
- **通道分层（别把红石当主力）**：跨计算机通信的主力是**进程内总线 / 私有信号**（float32、按名寻址、
  不经世界方块、不占世界机制资源 —— 见 `SignalBus` 的 `ConcurrentHashMap<String, Float>`）；**Create 红石链接是通信兜底**，
  只用于与原版红石 / 他人模组 / 非本模组装置互操作；执行侧另有动力指令（±256 RPM 浮点）。
- **代价（长期风险）**：**对世界的耦合面仍然窄** —— 兜底通道只能读写 0–15；**读不了任意方块状态**
  （库存 / 物流 / 机械相位），也驱动不了非动力的 Create 执行器（轴承 / 活塞 / 绳索 / 列车）。装置式方案
  可以直接与世界里的其它方块做**物理**耦合（贴在一起就行）。
- **正面解法（已排期）**：**1.3.0 计划公开 API**，供模组开发者做高精度控制联动 —— 这条窄口的第一顺位解法，
  落地后本节的风险降级为"待实现的能力项"（§7.10 反悔条件③）。

### 7.9 五条"底牌"的真实成色（先说结论）

| # | 看起来的优势 | 结论（先给判定） |
| --- | --- | --- |
| 1 | 链式 0 tick 传播 | **只保证"方块之间"**，且换来 20 Hz 与性能无保证、对外通信 1 tick |
| 2 | 出口只能到整数级 | **只在红石通道成立**：我们另有一条 Create 原生的动力通道 |
| 3 | 空闲零成本 | **我们也有**，而且优先用在最贵的地方（公式节点） |
| 4 | 单回路打磨深度 | **这条是真差距**（唯一一条） |
| 5 | 零外部依赖 | **是"红石方块式"的天然属性，换不到部署面** |

1. **"同 tick 链式传播"只在方块之间的链上成立，代价是 20 Hz 与性能无保证、对外还要过 1 tick。**
    - 链内递归直调确为同 tick ✓（§7.11-1）；但**与外部世界（原版红石 / 其他模组）的通信只能走原版邻居通知 + 0 延迟计划刻**，实测要 **1 tick**（作者口径）。
    - 它的求值挂在**计划刻队列**上（常开族每 tick 自我重排一次，§7.11-1），而邻居通知还在往同一条队列插任务 —— 这条队列**全服共享、每 tick 有上限**（§7.4 场景 B），装置越多、邻居越复杂，控制周期越容易掉到 20 Hz 以下。**"0 tick"是拿"周期无保证"换来的。**
    - 我们走的是**方块实体刻列表直接调用**，不排那条队（代价是我们每 tick 恒定成本，见 §8.4）。
2. **"出口只能到整数级"只在红石通道成立 —— 而红石在本模组里只是兜底通道。**
    - **跨机主力 = 进程内总线 / 私有信号**：float32、按名寻址、不经世界方块（`SignalBus` 的值类型就是 `Float`；"频段"只是编辑器里的名字列表，不是量化）。→ 计算机之间的高精度联动**本来就不走 4 bit**。
    - **红石链接 = 通信兜底**：只用于与原版红石 / 他人模组对话（§7.8）。
    - **执行侧 = Create 原生转速接口**：动力成员（可变速器 / 数控齿轮箱 / 转速代理）直接下 **±256 RPM** —— 变速器走官方 SpeedController 的**浮点目标转速**，转速代理走滚动值（整数 RPM 一步）；读回是**浮点**转速 / 应力 / 容量。
    - 于是 0–15 的整数限制只落在这三条里的**兜底通道**上 → "亚级分辨率"是**红石通道**的缺口（§9.3-1），不是整体缺口。
3. **"空闲零成本"我们也有，而且优先用在最贵的地方。**
    - **公式节点**：完成且输入未变 → **整节点跳过**（输出保持）；同 tick 同脚本同输入还有去重缓存（§8.5 的 `dedupHits` / `dedupMisses` 就是给它计数的）。
    - 触发器差分、动力读数推送：只在变化时下发。
    - 未做的只是**图级短路**（廉价代数节点仍每 tick 遍历，100–300 ns/节点，§8.1）—— 那是优化，不是"没有缓存"。
4. **单回路打磨深度：这条是真差距。** 对方有多级积分 / 微分链、每侧控制端模式、自校正预测；我们只有单级 I/D（另有积分死区保持、I 项限幅 + 原始积分钳制、scale，§7.11-6）。
5. **"零外部依赖"是"红石方块式"的天然属性，但它换不到部署面。**
    - 它仍是一个必须装进服务端的模组 → **进不了原版服 / 纯插件服**："零依赖"没有把它带进任何我们进不去的环境。
    - 而我们对 Create 的依赖与目标用户圈本就重合（本模组是 Create 附属），且依赖面**同生态**（§9.5-2 的 Mixin 是需要盯的那一处）。

→ **净结论**：五条里第 1 条要打折（只对内）、第 2 / 3 / 5 条我们不亏、**只有第 4 条是真差距**。
→ 于是"待补清单"只剩两项：**红石通道的抖动输出节点**（成本最低、收益直接）与**单回路功能对齐**（多级 I/D、每侧模式）。

### 7.10 结论：动因、代价、反悔条件

**动因（成立）**：立项要覆盖的三类用例里，后两类（交叉耦合、解算 / 反解）**只有节点编程能表达**（§7.3）；
在能表达的范围内，典型规模下我们的主线程 / GC / 世界机制触发都更省（§7.4 / §7.5），
且**全部成本都落在自己能设上限、能观测的地方** —— 节点上限、预算池、埋点、广播策略（§八）。

**代价（如实）**：

| 代价 | 量化 / 位置 |
| --- | --- |
| 代码面积：解释器 + 图 + 编辑器 | 全仓 45,326 行（对照方案 7,503 行） |
| 红石出口精度吃亏（动力出口不受限） | 红石 0–15 无抖动、20 Hz 上限、跨宿主 0/1 tick 抖动（§7.6、§7.9-2） |
| 重公式有秒级时延 | 默认预算下 ~2.5–3.3 s / 解算（§8.6） |
| 极端规模会撞 GC 门槛 | 20 台同时解算 ≈ 520 MB/s（§7.4） |
| 对世界的耦合面窄 | 跨机走进程内总线（float32）不受限，但**兜底红石通道只有 0–15**，且读不了任意方块状态 / 库存 / 物流；**1.3.0 计划公开 API 是正面解法**（§7.8、§7.9-2） |
| 外部依赖脆 | Create 方法签名 Mixin（§9.5-2） |

**反悔条件（什么时候方块式方案才是对的选择）**：

1. 目标只到第 ① 类（单 / 多轴 PID + 加减）—— 对方 16–32 方块就能干完，且 0 tick、亚级输出都赢；
2. 追求亚级输出精度，且不接受补"抖动输出"节点；
3. **装置必须与世界里的其它方块做物理耦合**（Create 动力、物流、机械交互）—— 兜底通道太窄
   （**正面解法已排期：1.3.0 公开 API，供模组开发者做高精度控制联动**）。

→ 当前三条都不成立（第 ① 类只是我们能力的一个子集；第 2 条有低成本补法；第 3 条是待改善项而非立项前提）。
但**第 3 条要盯着**：若将来的主要用例变成"与 Create 机械深度联动"，它会从"待改善"变成"选错路径"。

### 7.11 附：对照方案的机制复核（传播 / 持久化 / 精度 / 控制回路）


> 本节只谈**机制**，不指名任何模组。标 `【核实】` 者为读源码确认，`【静态推断】`者为结构推出、未实测。

#### 7.11-1 传播模型：0 延迟计划刻 + 同 tick 递归直调 + "每 tick 只算一次"的访问标记【核实】

对照方案的跨方块传播**不是**靠原版邻居更新被动重算，而是三段叠加：

1. **触发**：方块值变化时，主动向六面邻居发一次方块更新，并给每个方块式邻居**排一个 0 延迟计划刻**；
2. **同 tick 递归直调**：算出新值后，**直接递归调用**六个邻居的求值入口（不是"等下一 tick"）→ 这是它"链式 0 tick"的真实来源；
3. **访问标记**：每方块记录"本 tick 已算过"，于是同一 tick 内的重复访问被丢弃——**既做去重，也做环终止**。

**量化（每次输出变化）**：1 次邻居通知扇出 = **6 次 `neighborChanged`** → 每个方块式邻居各排 **1 个 0 延迟计划刻**（共 6 个插入）+ **1 次方块更新包**。
**空闲方块**：0 成本（只有值变化才触发）。
**常开族**（PWM / PID 系 5 类方块）：每 tick 自我重排一次计划刻 → 每 tick 恒定一次求值 + 一个计划刻对象【核实】。

#### 7.11-2 计数口径更正（旧稿"12 次 `updateNeighborsAt`"）【核实】

旧稿把"6 次邻居通知"与"两条触发路径"重复计数，写成了"12 次 `updateNeighborsAt`"。
逐条核对后的正确口径是 **1 次邻居通知扇出（6 次 `neighborChanged`）+ 6 个 0 延迟计划刻插入 + 1 次方块更新包**。
**量级结论不变**（每方块每次变化仍是 6–12 次世界机制入口），但"12"这个数字本身应作废。已记入 §附录 C。

#### 7.11-3 "0 tick 就一定收敛"是错觉：汇聚扇入处同样不确定【静态推断】

访问标记的语义是"**同一 tick 只算一次**"。因此在**菱形扇入**（A→C、B→C）下：
先到达的上游让下游算出结果并打上标记，**后到达的上游不会再让下游重算** → 下游在本 tick 用的是**混合了新旧的输入**。

**对本模组的意义（这条要写清楚，别自欺）**：

- 我们和对照方案**是同一类问题的两种形态**，差别在**位置**与**是否自愈**：
    - 本模组：每个宿主每 tick 全体重算 → 最坏**错 1 tick**，下一 tick 自愈；
    - 对照方案：纯传递方块**可能把那个陈旧值保持到"下一次输入变化"**为止（因为它只在输入变化时才重算）；自带每 tick 重排的常开族则会在本 tick 内自愈。
- 所以"对方链式 0 tick"这条优势**只在无汇聚的链上成立**；有扇入的控制回路里，双方的差异比直觉小。
- ⚠️ 这条是**静态推断**：需要在游戏内构造菱形扇入装置实测（可复用 §6.4 步骤 0 的双机对比方案）。

#### 7.11-4 状态持久化对照【核实】

| 项 | 方块式方案 | 本模组 |
| --- | --- | --- |
| PID 积分 | 存 NBT（×10⁵ 定点整数，5 位小数） | 存 NBT（运行时状态里的 PID 表） |
| 增益 / 模式 / 限幅 | 存 NBT | 存 NBT（节点参数） |
| 抖动累加器 / 上一拍输入 / 控制端边缘状态 | **不存**（重登后瞬态归零） | 部分存（边沿记忆在运行时状态里） |
| 纯传递方块的输出 | **不存** → 区块重载后归零，直到下一次输入变化 | 快照 + 运行时状态随 NBT |
| 双轴方块的第二轴状态 | 两轴读同一组 NBT 键 → **第二轴状态不独立序列化** | 不适用（图内各节点独立 id） |

→ **结论**：持久化这一项**本模组更完整**；对方的瞬态丢失是"方块式方案"为了省状态而付的常态代价。

#### 7.11-5 精度与输出分辨率【核实】

| 项 | 方块式方案 | 本模组 |
| --- | --- | --- |
| 内部信号 | 整数，标称 **[-15,15]**；S 系按 4 bit 幅值 + 符号打包，3–4 个值塞进一个整数 | **float32**，无位宽约束 |
| 面向原版的出口 | 0–15（部分方块另有**抖动累加器**，给出时间平均的**亚级**分辨率） | **四舍五入 + 钳到 0–15**，**无抖动 / 无 PWM 出口** |
| PID 计算 | 双精度，但输入是整数子级，小数部分靠"预测"补（不是实测） | float32，输入即浮点 |

→ 两条方向相反的能力差：**内部位宽我们赢**（float32 + 图 + 公式），**出口分辨率对方赢**（抖动 / PWM）。
在"用 15 级红石驱动舵面"这类用例上，对方能把 3.7 级这种量表达出来，我们只能给 4 级。
**这是我们能力清单里一条真实缺口**（§9.3-1）。

#### 7.11-6 控制回路功能对照【核实】

## 八、性能基线与埋点（本模组自身）/ Performance Baseline and Instrumentation (this mod)

> 本节只算**自己**的账：复杂度事实、每节点成本、候选优化、广播量级、埋点规格、重脚本实测、预算档位、以及远期选项。
> **与对照方案的比较、以及立项论证在 §七** —— 本节继续引用 §7.4 / §7.5 的结论，不重复论证。
> **口径声明**：除非标注 `【核实】`，以下为**静态推算**（读代码 + 复杂度核实 + 量级估算），**非 profile 数据**。

### 8.1 已核实的复杂度事实【核实】


| 事实 | 机制 |
| --- | --- |
| 节点查找 **O(1)** | 节点图持有 id → 节点的哈希表 |
| 每引脚取值 **O(1)** | 一次输入缓存查表（已优化掉"两次查找"） |
| 输入缓存只在连线变化时重建 | 由拓扑失效触发 → **稳态每 tick 无结构计算** |
| 环节点不进拓扑序 | Kahn 只收入度归零者 + 求值只遍历有序表 → 每节点每 pass **恰好求值一次** |

→ 稳态求值是 **O(N)**，**不是** O(N²)/O(N·E)。这是"1024 节点仍 <1ms"成立的前提。

### 8.2 每节点每 tick 的成本清单【估算】


| 每节点每 tick | 复杂度 | 分配 |
| --- | --- | --- |
| 节点查找 | O(1) 哈希 | `Integer` 装箱（<128 命中缓存） |
| `params` 存 / 取 | O(1) | 无 |
| 参数引脚覆盖 | O(参数引脚数)；无引脚=0 | 有覆盖时 `params.clone()` |
| 每输入引脚取值 | O(1) 查表 | **`Long` 装箱**（packed key 远超 Long 缓存范围） |
| switch 体 | 5–30 次浮点 / 整数 | FORMULA：`new float[输入数]` |
| 输出写入 | O(输出引脚数) | **`float[]` 分配 + 复制 + `Integer` 装箱** |
| 收尾扫 `REDSTONE_OUT` | 每 pass O(N) | `ArrayList` + 结果对象 |

**纯算术量**：1024 节点 × ~20 flops ≈ 2×10⁴ 次运算 → 现代 CPU（3–4 GHz，JIT 后简单浮点 10⁷ ops/ms 量级）≈ **0.002 ms**，**占总开销不到 1%**。

**固定开销**：哈希查 + 装箱 + 数组分配 + 分支 / 缓存未命中 ≈ 100–300 ns/节点
→ 1024 节点 ≈ **0.1–0.3 ms/tick**，占一个 tick（50 ms）**约 0.3%**。

> **与作者实测"巨量普通节点状态下每 tick < 1ms"吻合**，且解释了原因：
> **瓶颈是每节点固定开销，不是运算量**（ALU 远未成为瓶颈）。
> 推论：FAQ 里"单计算机 PID 不宜超过 5–6 个"是 **v1.0.0 初版**遗产，现已被实测推翻（见 §附录 C）。

### 8.3 候选优化 1：删掉一层冗余克隆（热路径，零行为变更）


快照捕获**已做完整深拷贝**（每节点新建 HashMap + 值数组克隆；子图再拷一层），
而求值器把结果放进输出表时**又 clone 了一次** → **每节点每 tick 被克隆两次**。

内层克隆的语义价值经核实**为零**【核实】：

- 跨 tick 消费者**全部**走快照（显示器渲染、显示器编辑器、客户端求值包）
- "获取当前输出表"的访问器**零消费者**
- 每个 pass 开头都会清空输出表 → 外部保留引用本也读不到东西
- 单 pass 内别名安全：环节点不参与求值，每节点每 pass 恰好写一次

→ **收益**：省 1024 次 `float[]` 分配 + 复制 / tick / host（20 Hz 下约 **2 万次 / 秒 / host**）。
→ **前提**：补一条单测锁死"跨 tick 只读快照"这个不变量后再删。
→ **优先级**：当前 <1 ms 无感、**不急**；但它是热路径上的纯浪费，且**与立项动机（GC 压迫）直接相关**——每节点 ×2 数组是服务端求值路径里主要的分配源之一（§7.5），抬高节点上限或多 host 规模化时是第一个该动的。

### 8.4 广播是 O(N×P)（需埋点先行）


| 每 tick | 复杂度 | 随玩家数放大 |
| --- | --- | --- |
| 求值 | O(N) ≈ 0.1–0.3 ms | ❌ |
| 红石输出写出（红石链接网络更新） | O(REDSTONE_OUT 数)；代价落在 Create 侧 | ❌ |
| 快照捕获 + 广播 | 每节点再克隆 + 装箱 + 逐输出写浮点 + **每个追踪玩家一次序列化 + 发包** | ✅ **O(N × P)** |

按同一口径，**每节点序列化成本为数倍于求值成本**，且**乘追踪玩家数 P**：

- P = 1：广播 ≈ 求值量级
- **P ≥ 2–3：广播超过求值**
- P = 10：可能贵一个数量级

→ 即："求值便宜"这个事实把目标锁定在**广播**上；这与 §3.4 的脏缓存 / 增量广播是同一件事，现在有了量化依据。
→ 阈值需埋点数据支撑（见 7.5），不要凭估算定策略。
→ **本轮补充（§9.2-3）**：广播路径目前**无变更检测、无增量、无节流**，每次调用都是全图重打包。

### 8.5 埋点规格（`perf` 命令的数据来源）


**现状：全仓无耗时埋点。** 仅有的 4 处 `nanoTime()` **全是节流非测量**；运行时状态里的 `debugTime` 与包里的 `debugTimes` 是调试节点的**相位累加器**，**不是耗时**。

```
GraphHost 求值段三段包夹（仅 config 开关打开时执行）：
  t1 = nanoTime();  evaluate(...);          t2 = nanoTime();   → evalNs
  writeOutputs(...);                        t3 = nanoTime();   → writeNs
  broadcastEvalSnapshot();                  t4 = nanoTime();   → castNs
每 host 维护 3 个环形窗口（近 100 tick 的 avg / max / p99），零分配
默认关 → 零行为变更、零常开开销
```

`perf` 命令同时接上既有计数器：预算总额 / 本轮 slice / 重公式数 / 去重命中与未命中
（§4.3 提到的那几个"孤儿访问器"在这里获得首批消费者）。

> ⚠️ **本轮补充**：其中"过期判定"这个访问器**没有实现兜底语义**（无调用点，§5.5 修正）。`perf` 若要把它接上，要么先按 §9.2-1 接线，要么在输出里明确标"未接线"。

**分配量埋点（GC 压迫问题专用）**：`nanoTime` **测不出分配**。要量化"分配速率 → 新生代停顿"，加一项：

```
每 tick（或每 N tick）采样 ThreadMXBean.getThreadAllocatedBytes(currentThread)
→ delta = 本 tick 分配字节数，与三段耗时同样进环形窗口
配套：JFR 事件 jdk.ObjectAllocationSample（定位分配源）+ JVM -Xlog:gc（看停顿）
```

判据：设计目标是**分配速率与停顿**，不是堆占用曲线——"堆过大"只是表象，
真正要压的是 **bytes/tick × 20** 与由它决定的新生代收集频率（见 §7.5）。

### 8.6 实测脚本分析：弹道反解火控（作者提供的 `ballistic_solver.txt`）


脚本 192 行：`DT=0.05`，**361 点俯仰粗扫描** + 牛顿精化（≤50 轮 × **每次 3 个仿真**：f / f+ / f−，中心差分，阻尼 0.5），
内层仿真 `repeat 1200`，`break` 条件 `py < ty - 60`。

**结构成本**

| 阶段 | 仿真次数（上限） | 说明 |
| --- | --- | --- |
| 粗扫描 | **361** | 每仿真 ≤1200 步；**主成本** |
| 牛顿 | ≤50 轮 × **3** | 中心差分需 3 次仿真 / 轮 |
| 末次验证 | 1 | 求 `hit` |

→ 牛顿首轮就要 3 次仿真，而粗扫要 361 次 → **粗扫占约 78% 的仿真次数**。

**每内层步的分配（关键）**
`d = dist(vec3(px,py,pz), vec3(tx,ty,tz))` + ~15 条赋值
→ **2 个向量值 + ~15 个标量 ≈ 17 个对象 / 步**（record 装箱），外加 **2 次 `sqrt`**（`sp` 与 `dist`）。

**量级（估算）**

| 项 | 数值 |
| --- | --- |
| 步数 | 粗扫 361 × 平均 ~500 ≈ 180k；牛顿 ~10–30 轮 × 3 × ~500 ≈ 15–45k → **~200–230k 步 / 解算** |
| 分配 | 230k × 17 ≈ **4M 对象 ≈ 100 MB / 解算**（比 §7.4 初估的 24 MB 高 4×） |
| 计算 | 按 0.5–1 µs/步 → **150–200 ms / 解算** |
| 解算时延 | 默认 3 ms/tick → **≈ 50–65 tick ≈ 2.5–3.3 s** |
| ⚠️ 多路火控 | 预算总量固定（`slice = 预算 / 重公式数`）→ **时延 ∝ 同时解算的重公式数**；2 台同时解算 → 每台 1.5 ms/tick → ~5 s |

**可优化点（按收益 / 成本排序）**

1. **热启动（最大收益）**：火控是连续闭环，**上一解就是极佳初值** → 用 LATCH / 私有信号把它反馈为初值输入，把 361 点粗扫换成 ±3 步局部扫描 → 仿真次数 **361 → ~7（−98%）**，解算时延降到 **~1–2 tick**。注意：现有 `warm` 开关管的是"spread 中途输入变化"，**不是算法热启动**，这是脚本层可控的优化。
2. **早退**：`mind` 只需"最近距离" → `d` 连续增大多步即可 break；现在要等 `py < ty-60`，放行了大量无效步。
3. **去 `sqrt`**：距离比较用 `d² < mind²`（单调等价），只在最后对 `mind` 开一次根 → 每步省 1 次 `sqrt`。
4. **去 `vec3`**：`dx/dy/dz` 三个标量替代 `vec3(...) + dist(...)` → 每步省 **2 个向量对象**；即使保留 vec3，也应把目标点常量提到循环外（**每步都在重建常量目标点**）。
5. **牛顿 → 黄金分割 / 二分**：现在是对**非负距离函数**做牛顿，最小值处导数趋零使步长爆炸（靠阻尼 0.5 + 范围检查兜住），且**每轮 3 次仿真**；粗扫已给出包围区间，**黄金分割每轮仅 1 次仿真**，更稳且省 3×。
6. **末次验证可省**：`f < 0.001` 分支退出时，最后一次仿真算出的就是最终距离 → 末段是冗余仿真（≤1200 步）。

**⚠️ 与迭代上限的关系（必须实测）**
按"语句 / 迭代"口径计，粗扫满跑（361 × 1200 × ~15 语句）**远超上限** → 会硬 shed 到 `lastGood`。
是否触发取决于迭代口径与 `break` 的实际早退率。**必须实测最坏场景的总迭代数并留 2× 余量**；
注意不可达（`hitf == 0`）走 `bestp` 路径、不触发 shed。

### 8.7 预算档位的影响（3 ms vs 20 ms）


配置项 `formulaBudgetMs` 的范围是 **0.5–20.0，默认 3.0**。
口径：deadline 每 tick 复位、**全服共享**（`slice = 预算 / max(1, 重公式数)`，保底零饿死）→ **20 ms 是"每 tick 总量上限"，不是"每个公式的配额"**。

以 §8.6 的实测脚本（~200 ms 解释器时间 / 解算）为基准：

| 预算档 | 占一个 tick（50 ms） | 解算所需 tick | 解算时延 | MSPT 余量 |
| --- | --- | --- | --- | --- |
| 0.5 ms | 1% | 400 | ~20 s | 舒适 |
| **3.0 ms（默认）** | 6% | ~67 | **~3.3 s** | 舒适 |
| 10 ms | 20% | ~20 | ~1 s | 需监控 |
| **20 ms（上限）** | **40%** | **~10** | **~0.5 s** | 仅当 tick 基线 < 25 ms 时可行 |

**四条关键性质**

1. **时延 ∝ 1/预算，且 ∝ 重公式数**：`slice = 预算 / 重公式数` → 总量固定。20 ms 下若有 4 个重公式同时解算，每个只分到 5 ms → 各自 ~40 tick ≈ 2 s。**"调大预算"对多路火控是共享稀释，不是各自加速。**
2. **预算池不知道 tick 的其余开销**：它是**绝对上限**，不是 tick 的百分比。服务器基线本来 45 ms 时，20 ms 会直接叠上去 → 掉 TPS。**高负载下必须看 MSPT，而不是只看预算档。**
3. **墙钟 ≠ CPU 时间**：切片与过期判定都用 `System.nanoTime()`
   → **GC 停顿 / OS 调度会直接吃掉预算**。3 ms 档下一次 5–10 ms 的 young GC 停顿 = 该 tick 解算几乎零进展；
   20 ms 档抗抖动明显更好。**这是提高预算一个反直觉的加分项**（对 §7.4 的 ~520 MB/s 分配场景尤其相关）。
4. **迭代上限不受预算影响**：预算只改"每 tick 做多少"，**总迭代数不变** → 若某场景确实需要超过上限的迭代，
   任何预算档都救不了（硬 shed 到 `lastGood`）。**降迭代是算法层的事（§8.6），预算不是解药。**

**结论 / 建议**

- **20 ms 能让火控从"~3.3 s 滞后"变成"~0.5 s"，是本脚本下最省事的提速手段**；但它花掉 40% 的 tick，且与 §7.4 的高分配场景叠加会放大 GC 抖动（性质 3 同时是好消息）。
- **更优路径是 §8.6 优化 1（热启动）**：总迭代降 ~98% → **3 ms 档即可 1–2 tick 完成**。
  此时应**把预算下调**（而非上调），让病态脚本咬不到一大块 tick——即"**算法提速 + 低预算兜底**"优于"**算法不变 + 高预算硬扛**"。
- 若两者都要：**热启动 + 20 ms** → 亚 tick 完成；但没必要长期开着 20 ms。

### 8.8 远期选项：Rust 后端胶水（1.3.0+）的收益边界


> 形态假设：**首 tick 放值 → 尾 tick 取结果** 的胶水模型（Java 侧只管交接，计算在原生侧）。
> 以下全部为**静态估算**，且**收益高度依赖两个未定变量**：搬哪一部分、同步还是异步取结果。

**两个变量决定收益差一个数量级**

| 变量 | 选项 | 后果 |
| --- | --- | --- |
| **搬什么** | (a) 只搬 FORMULA 解释器（纯函数、无跨 tick 状态、已有挂起 / 载体机制） | 收益最大、风险最小 → **推荐** |
| | (b) 搬整个图求值（PID / 时序 / ENCAP / 总线读写） | 需把运行时状态 + 总线 + 红石 I/O 过界 → **跨语言调用成本会吃掉小图的全部收益**；且状态双份 |
| | (c) 搬 Sable 物理 / 姿态 | 不可行（他人对象） |
| **怎么取** | 同步等结果（尾 tick 阻塞） | 主线程照样付全部计算时间（只是换个地方付），且**不可抢占 → 抖动更差** |
| | 异步取上一轮结果（尾 tick 非阻塞） | 主线程只付 µs 级交接 → **但输出按设计陈旧 k tick**，且与逐 tick 状态节点（PID / 延时 / 触发器）**语义冲突** |

**量化（以 §8.6 的实测脚本与 §8.2 的图求值为基准）**

| 优化对象 | 现状 | Rust 后（估） | 加速 | 说明 |
| --- | --- | --- | --- | --- |
| FORMULA 解算 | ~200 ms / 解算 | 20–40 ms（原生解释器）/ **2–4 ms（AOT 编译成本地函数）** | **5–10× / 50×** | 装箱消失是主因 |
| **公式 GC** | **~100 MB / 解算**（4M 个中间值对象） | **≈ 0** | **~∞** | 服务器规模下 **§7.4 的 520 MB/s → 数十 MB/s**，**这是最可量化的一项** |
| 图求值 | 0.15 ms/host/tick @1024 节点 | ~0.01 ms | 10–15× | 纯算术占比 <1%，理论上界=消掉全部固定开销；**但绝对值仅 0.14 ms/tick/host，不值得为它搬状态** |
| 主线程公式预算占用 | ≤ 预算档（20 ms 档 = 40% tick） | 异步模型下仅 µs 级交接 | — | 代价：输出陈旧 + 状态一致性 |
| **广播 / 快照** | O(N×P) | **不变（仍在 Java 侧）** | **1×** | **Rust 之后瓶颈会转移到这里**（§8.4） |

**代价与风险（工程面，往往比收益更重要）**

- **多平台原生库**：Windows/Linux/macOS × x64/ARM → 发布体积 + 构建矩阵；**必须保留 Java 回退路径**（平台不支持 / 加载失败）→ **双实现长期维护**
- **状态归属**：运行时状态（PID 积分 / 延时队列 / 触发器 / 公式载体）是权威状态。放 Rust → NBT 迁移、多人同步、蓝图兼容、崩溃一致性全部要重做；放 Java → 只搬纯函数最稳
- **可调试性**：JFR / JVM 工具看不见原生侧；**原生崩溃 = 整个 JVM 死**，`try/catch` 拦不住
- **调用成本**：JNI/JNA ≈ 10–50 ns/call、Panama 类似；**必须批量交接**（整图一次进、一次出），否则小图净亏

**结论：Rust 是第 4 优先级，不是第 1**

```
① §8.6 脚本优化（热启动 −98%，改脚本，几天）
② §8.3 去冗余 clone + §8.5 埋点（小改动，可量化）
③ §8.4 广播增量化 / 节流
④ 仍不够，再上 Rust（几个月 + 多平台原生库 + 双实现维护）
```

**核心理由**：热启动把 200 ms 降到 ~4 ms（**−98%**），已经**超过** Rust 解释器级的 5–10×，
而成本是"改一份脚本"对"多平台原生库 + 双实现"——**差两个数量级**。
Rust 真正无可替代的价值是 **GC 归零**（公式装箱），而这一项**用 Java 侧 primitive 栈（§十一 开放问题 ⑩）也能拿到大部分**，
代价只是改动求值器内部表示（不引入新的运行时依赖）。**先穷尽 Java 侧手段，再考虑跨语言。**

## 九、本模组短板清单 / This Mod’s Known Shortcomings

> 口径：**A 时序与确定性 / B 规模与资源 / C 能力边界 / D 健壮性与安全 / E 工程与文档债**。
> 每条给 **机制 → 影响 → 性质 → 建议处置**。标 🆕 者为**本轮新发现**（此前无文档记录）。
> 本节只描述问题，不代表已排期；是否修由 §十一 开放问题逐条决策。

### 9.1 时序与确定性

**9.1-1 固定 `dt`：九个求值入口全部硬编码 0.05 s**【核实】

- **机制**：所有宿主的求值调用都传入字面量 `0.05f`（蓝图 / 程序计算机 / 转速代理 / 显示器 / 数控齿轮箱 / 传感器 / 可变速器 / 控制椅 / 雷达）。PID 的 I 与 D、积分器、齿轮箱的开环行程换算全部按"每秒 20 tick 整"计算。
- **影响**：服务器掉 TPS（40 ms/tick 甚至更差）时，**控制律与墙钟脱节**：积分项按"理想 tick 数"累积，D 项按 0.05 归一化 → 同一套增益在不同负载下表现不同。也**无法表达"以秒为单位"的控制律**（如"3 秒内到位"）。
- **性质**：核实（代码）；行为影响的量级未实测。
- **处置**：短期在节点 / 文档口径上承认"dt = 名义 0.05"；中期可引入"实测 tick 时长（平滑值）"作为 dt 源，但要一次改完九处（§6.3 收敛后只有一处，**这是收敛的又一条理由**）。

**9.1-2 跨宿主 0/1 tick 抖动 + 私有信号的无主残留**【核实】

- **机制**：见 §一。补充一项本轮发现：**宿主停机路径不清私有信号**——停机只清 BUS 的内部映射与红石输出，**私有信号仍留在进程内表里**；而节点注销 / 停服 / 编辑器改名删除三条路径是完整的。
- **影响**：停图 ≠ 撤值。外部读者会继续读到停图前的私有信号，直到区块卸载把它清掉（此时**值又突然变 0**）→ 两种不一致的边界行为。
- **性质**：核实（代码）。影响面取决于是否有外部订阅者。
- **处置**：并入 §6.4 步骤 2（维度前缀那次提交），顺手把停机路径补上；观测设施的 `topo` 会直接暴露"谁在读一个已停 host 的私有通道"。

**9.1-3 环路静默停更**（§5.6 已记录，此处只登记为短板）【核实】

- 图内拓扑排序不把环节点放进有序表 → 跨 BE 通道环会让**整条环上的 host 静默停更**，且编辑器看不见跨 BE 环。这是 C 阶段 `ring` 命令的立项理由。

**9.1-4 求值入口分三档，导致时序节点在部分宿主上静默失效**【核实】🆕

- **机制**：十个宿主的求值调用分三档：
    1. **真实状态表**（传运行时状态里的延时队列 / 锁存表 / 脉冲计时表）：蓝图、程序计算机、数控齿轮箱、可变速器 —— 时序节点正常；
    2. **每 tick 新建空表**：显示器、转速代理、动力仪表、雷达 —— 时序节点的状态**每 tick 被丢弃**；
    3. **无状态入口**（根本不走时序节点的求值分支）：控制椅、传感器 —— 时序节点在该宿主上**不参与求值**。
- **实际影响**：节点准入清单里，**动力仪表放行了逻辑类节点，而逻辑类里的"门控"节点是带锁存状态的** → 该宿主的门控节点每 tick 从参数默认值重新开始，**锁存语义失效**（表现为"门永远按默认状态开合"）。其余宿主当前是**潜伏**的：它们的准入清单恰好没放行时序 / 锁存类，一旦未来放行就会立即变成活 bug。
- **性质**：核实（代码路径 + 准入清单交叉核对）。用户可见影响需要一台仪表现场复现确认。
- **处置**：**优先级最高的"便宜修复"**——统一到第 1 档（真实状态表）即可，或在准入层显式排除"需要状态"的节点类型并加一条 UI 提示。它也和 §6.3 收敛同向。

### 9.2 规模与资源

**9.2-1 预算兜底未接线：过期判定无任何调用点**【核实】🆕

- **机制**：预算池每 tick 建立 deadline，并提供一个"是否过期"判定，但**该判定没有任何调用点**；真正生效的只有"循环边界按片让出"。也就是说：**无循环的重脚本（一次性长表达式）没有任何切分点，可越界**；昂贵循环体也只能在边界处被切，单次越界幅度取决于循环体本身。
- **影响**：文档与 FAQ 把"每 tick 预算上限"讲成了既有设施，**实际存在越界窗口**。这是"文档承诺 > 实现"的典型。
- **性质**：核实（全仓调用点搜索）。
- **处置**：二选一——① 在解释器入口 / 表达式求值入口补上"过期即挂起"（同时按 §5.5 搬迁基准）；② 明确降级为"按片让出，非硬兜底"，并把文档改口。**不要继续让文档替未接线的机制背书。**

**9.2-2 去重缓存会缓存"挂起 / 出错"的结果**【核实】🆕

- **机制**：公式节点无论走完、挂起还是抛异常，最后都会把结果写进去重缓存（键 = 脚本源 + 引脚输入）。
- **影响**：同一 tick 内若有**两个相同脚本 + 相同输入**的节点，第二个会拿到第一个的**冻结值或归零值**，而不是自己算。挂起时两者通常等价（都该冻结），但**出错路径会把"零"扩散给本来能算的节点**。
- **性质**：核实（代码顺序）；触发条件苛刻（重复脚本 + 挂起 / 报错）。
- **处置**：把"出错"结果排除出去重缓存（一行判断），挂起结果是否缓存需明确语义后再定。

**9.2-3 全图快照广播：无变更检测、无增量、无节流**【核实】🆕

- **机制**：宿主每 tick 调一次广播，广播内部无条件捕获全图快照并打包发给所有追踪玩家；没有"值没变就不发"的短路，也没有降频。
- **量级**【估算】：1024 节点 ≈ 7 KB+/tick/玩家 ≈ **140 KB/s / 方块 / 玩家**；P 个玩家即 ×P。客户端还要每包重建哈希表与数组 → 客户端 GC 也被带动。
- **对照**：方块式方案在"空闲"时是 0 成本（只有值变化才发包）；本模组**恒定成本**。这不是 bug，是"每 tick 全体重算 + 全量同步"的定价。
- **处置**：等 §8.5 埋点（`castNs`）给出 P=1 / P=3 的实测差值再定策略（增量 / 降频 / 差异三选一）。**先埋点，不要拍脑袋。**

**9.2-4 每节点每 tick 两次克隆 + 高频装箱**（§8.3 已记录）

**9.2-5 节点上限只在编辑器把守**【核实】🆕

- **机制**：节点上限（1024）在客户端的"添加节点"入口判断，另有 UI 计数与超限 ⚠；**服务端 / 粘贴 / 导入 / 复制路径没有对应校验**；封装子图超限时求值直接**全零输出且不写日志**。
- **影响**：越限后的行为不是"报错拒绝"而是"静默降级"（子图全零）；对服务端而言，越限请求来自被改过的客户端时无任何拦截。
- **处置**：把上限判断下沉到服务端 op 执行层（与服务端限流同一批提交最省事）；子图超限至少补一条 WARN。

### 9.3 能力边界（诚实口径）

**9.3-1 红石出口是 4 bit 整数，且无抖动 / PWM**（动力通道不受此限）【核实】🆕

- **只指红石链接通道**：内部算 float32，但红石出口四舍五入并钳到 0–15、无时间抖动 → 在"用 15 级红石驱动舵面"这类用例上，有效精度低于对照方案。
- **动力通道不受此限**：可变速器 / 数控齿轮箱 / 转速代理走 Create 原生转速接口 —— 变速器用官方 SpeedController 的浮点目标转速、转速代理走滚动值（整数 RPM 一步、量程 ±256），读回是浮点转速 / 应力 / 容量（§7.9-2）。
- 另：红石输出必须经 Create 红石链接（两个频率物品配对），**没有方块面直连的红石模拟 / 布尔出口**。
- **处置**：① 给红石通道加"抖动输出"节点（时间平均给出亚级），成本低、收益直接；② 能力清单区分"红石通道 4 bit"与"动力通道 ±256 RPM 浮点"，别让用户以为 float32 只能走到 4 bit。

**9.3-2 20 Hz 硬上限，无亚 tick / 无线程外路径**【核实】

- 求值只在服务端 tick 内发生、每 tick 一次；执行侧还有可变速器的"每 4 tick 最多一次重构"的限速（见 8.3-3）。**无中断、无事件驱动快路径、无异步**。对"需要更快环路"的用例（高频振荡抑制、快速火控预判）这是硬边界。
- **处置**：写进 README / 设计文档的能力边界，不用"实时控制"这种会被误读的措辞。

**9.3-3 执行侧限速与无死区：可变速器每 4 tick 全拆重建**【核实】

- **机制**：变速器每 tick 对账"期望目标 vs 已应用目标"，**精确整数比较、无死区**；不一致且冷却（4 tick）已过 → 走一次完整的"脱网 → 断动力 → 清源 → 重挂"序列。
- **影响**：输出带 ±1 噪声的图会让动力网络**每 4 tick 被扰动一次**，长期如此；官方动力网络对高频反复接断有"闪烁摧毁"保护，风险由冷却窗口承担。**潜在世界伤害**，需要实测确认（构造 ±1 抖动的图跑一段时间）。
- **性质**：核实（代码：精确比较 + 冷却常量）；世界伤害未实测。
- **处置**：加**死区 / 迟滞**（例如目标变化小于阈值不重建），并实测重建频率上限。这是"控制回路打磨"里最该先做的一条。

**9.3-4 公式语言与显示能力的天花板**【核实】

- 公式内建函数集有限（缺 `abs/min/max/floor/sign/clamp/mod` 等常用项；`log` 只有单参形式；无用户函数、无数组 / 索引；比较只面向常量），引脚数上限（26 入 / 16 出）在超限时按校验 WARN 截断。
- 显示节点只有固定一位小数的数值渲染，**无标签 / 单位 / 精度设置**，与"仪表化"的能力叙事不匹配。
- **处置**：函数集扩容是低风险高收益项；显示格式建议作为独立需求排期。

### 9.4 健壮性与安全

**9.4-1 编辑 op 的越界索引可放大成服务端内存压力**【核实】🆕

- **机制**：像素序列的写帧 op 用"帧索引"作为扩容目标：`while (frames.size() <= 索引) { 新建一帧数组; 加入 }`；帧索引直接来自网络包，**没有上界检查**。同类形状还有"热键槽位 + 1"的数组扩容。
- **影响**：一个被改过的客户端可以发一个超大索引 → 服务端主线程循环分配直到 OOM / 卡死。当前该路径只对编辑会话成员可达（弱前置），但**这与 §4.4 的"不限 OP"路线叠加后风险上升**。
- **处置**：与 §6.4 步骤 2b（服务端限流）**同一批提交**：op 解码层加数值上界（帧索引、槽位、像素数组长度）。这是本次清单里**唯一一条"可被外部触发"的项**，建议优先。

**9.4-2 协作无权限模型**（§4.4 / 既有文档已记录）

- 距离校验 + 咨询式软锁；任何能走到 128 格内的玩家可编辑 / 删除任意图。已声明为非目标，但应写进对服主的说明。

**9.4-3 存在性 / 状态包无鉴权**【核实】

- 存在性上报包不做距离与会话校验，转发给同会话编辑者 → 可伪造他人光标 / 软锁（软锁是客户端咨询式，危害有限）。

**9.4-4 运行时错误对玩家不可见**【核实】🆕

- 公式语法错误在编辑器里有徽章；但**运行时**错误只写 DEBUG 日志并把输出归零；迭代超限只 WARN 一次、然后静默冻结在 `lastGood`，且"已警告"标记是 transient —— **区块重载后会再跑一次病态脚本**再警告。
- 对照：方块式方案出错会**广播到全服聊天**（噪声换可见性）。
- **处置**：给宿主编一个"图内有错误 / 已冻结"的可见状态（方块贴图或显示器角标），并把警告标记落 NBT。

### 9.5 工程与文档债

**9.5-1 文档自证不一致**【核实】🆕

**9.5-2 依赖 Mixin 挂在 Create 的固定方法签名上**【核实】🆕

- **处置**：在兼容层加一条启动期自检（方法存在性 / 行为探测），失败则明确报错而不是静默降级。

**9.5-3 求值入口分三档**（同 9.1-4；在工程债视角下它是"复制粘贴 10 份"的直接后果）

**9.5-4 姊妹计划的状态头过期，会误导排期**【核实】🆕
