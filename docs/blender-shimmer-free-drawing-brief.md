# Blender 节点编辑器「无闪烁（no shimmer/jitter）」绘制机制简报 / Blender Shimmer-Free Drawing — Method Brief

> **来源 / Provenance**：2026-11-14 子代理调研简报（方法论调研，GPL 红线执行：正文零代码/伪代码/源码文本，
> Blender 源码仅提炼行为规律写成散文；专有名词如 View2D、BLF 仅作名称引用）。
> 面向 Minecraft NeoForge GuiGraphics（整数坐标填充、无抗锯齿的立即模式 2D 渲染）图编辑器的设计输入。
> 与 [`graph-editor-canvas-jitter-plan.md`](graph-editor-canvas-jitter-plan.md)（抖动治理 JIT 系列）配套。
> 每条结论标注「确证（来源N）」或「推断」，来源见文末。

## 对本仓的启示（按性价比排序 / Implications for this repo, by cost-effectiveness）

1. **相机/平移整像素量化，且全场景共用同一取整相位**——残余「互相爬」的根因通常是各元素各自从分数相机位置独立取整；Blender 的做法是节点原点、插座、框内容共用一次整像素取整（同一原点 + 整数局部偏移），滚动条拖动甚至主动按每像素视图尺寸量化位移以防抖（确证，来源5、6、8）。这是零渲染成本、收益最大的一步。
2. **1px 线用「覆盖率软边」而不是裸线图元**——Blender 的描边是带 1px 线性/平滑羽化的条带（解析覆盖率混合），核心仍是满强度 1px，边缘半透明过渡到背景；蠕动本质是无 AA 时分数相位在两行像素间跳变（推断；确证部分见来源7、12、14）。MC 无 GPU AA 也可用 CPU 端 2-3 条半透明填充模拟同款羽化。
3. **文字与图标做像素对齐 + 离散字号档位**——字形按字号键控缓存、字号量化到极小定长步长，横向分数位置用亚像素档位补偿；节点原点取整的注释动机就是「文字永远像素对齐」（确证，来源8、9、10）。MC 位图字体天然有利：只允许整数位置 + 整数缩放档位即可消除字形蠕动。
4. **超采样放最后**——超采样（SSAA）只是把相位噪声平均掉，代价是整 GUI 渲到更大缓冲再缩；在 1+2+3 已解决相位问题后收益很小（推断）。连线的优先项是端点与框同相位 + 采样参数稳定化（贝塞尔按参数均匀求值、宽度定义在与缩放一致的空间），而非 AA 本身（确证，来源11）。

## 1. 变换管线（空间、次数、精度、取整位置）/ Transform pipeline

- **几何存储空间**：节点画布是一个二维「视图空间」（view space，即 View2D 的坐标系），节点位置、插座位置都是该空间的浮点坐标；节点内部内容（标题、插座、端口）以节点原点为基准的局部整数/浮点偏移存储。**确证（来源5、8）**。
- **变换次数**：每个编辑器区域（region）只有一个 View2D 映射把视图空间映到区域像素；节点、连线、网格全部经这同一次变换进入绘制，连线着色器直接吃同一个模型-视图-投影矩阵。**确证（来源5、11）**。全场景因此天然「同相位」——不存在每元素各自一套相机的问题。
- **精度**：View2D 的视图↔区域换算全程单精度浮点；可见视图矩形保持浮点、**从不量化到整数视图坐标**，只有输出为整数矩形时才在最后一步截断/钳制，浮点输出路径完全不取整。**确证（来源5）**。UI/2D 编辑器层没有 double（double 主要用于 3D 物体变换，属**推断**）。
- **取整到像素的步骤**：有，且位置非常明确——在「节点位置 → 绘制坐标」的换算处对**节点原点**做整像素取整，源码注释动机是「文字内容永远像素对齐」；**插座的运行时位置**同样取整，动机是「防止抖动（jiggle）」；折叠面板插座同样处理。**确证（来源8）**。其他取整点：widget 矩形本身是整数类型（布局产出即整数）；图标位置在宽高比接近 1:1 时吸附整数；UI 内部小构件（如颜色带手柄）对横坐标做「对齐到像素」的取整。**确证（来源7）**。
- **要点**：取整只做一次、做在最靠近「元素原点」的地方，元素内容用整数局部偏移挂在其下；映射本身（相机）保持浮点。这就是「相机连续、元素锁步」的组合——拖动时整个场景以 1px 步进平移，而不是各元素各爬各的。**推断（基于来源5、8的行为综合）**。

## 2. 边缘与框线（widget AA 机制）/ Edges & frames (widget AA)

- **widget 框线不是 MSAA，是解析式着色器边缘覆盖（analytic shader edge coverage）**：圆角矩形描边画成「外圈 + 内圈」两条顶点环之间的三角带，内圈恰内缩一个设备像素；着色器按各顶点属于内圈/描边带/浮雕层的标记与角部参数解析地计算边缘覆盖率，做平滑过渡。**确证（来源7）**（官方文档亦确认界面绘制走内置二维着色器，来源1）。
- **1px 线既清晰又不蠕动的配方**：几何上保持恒定 1 设备像素宽（描边带最小宽度约 1px，内圈按像素取整后的矩形计算），视觉上只在边缘做约 1px 的覆盖率羽化——核心满强度、边缘半透明，于是拖动时线的整体位置按整像素跳变，永远不会停在「两行像素各一半」的相位上闪。**确证（来源7）**（宽度/取整部分）+ **推断**（「不蠕动」的因果解释，与来源14的采样相位原理一致）。
- **纯直线不用线图元**：UI 里要求清晰的 1px 直线（下划线、分隔线）画成小高度的**填充矩形**（高度按像素尺寸取整），而不是走默认线光栅化；裸线图元默认无 AA。**确证（来源7）**（下划线为填充矩形）；「裸线默认锯齿」为**推断**。
- **装饰性小三角形图标**（箭头、对勾）用「抖动超采样」手动 AA：少量子像素偏移样本累积绘制、按样本数折算透明度；官方文档还记录了一条反例教训：图标若改用 GPU 抗锯齿，AA 所需的抖动会破坏图标的分层透明度设计。**确证（来源7、2）**。
- **理论锚点**：无 AA 时像素中心单采样决定覆盖，边缘呈阶梯；MSAA 用多重子样本按覆盖率比例混合颜色；纹理化 2D 元素位置哪怕轻微偏离像素网格，双线性采样结果就会改变（闪烁/蠕动的来源），补救是把几何对齐到像素边界（半像素约定）。**确证（来源13、14）**；「浮点几何 + 覆盖率 AA 不闪、逐帧取整相位变化才闪」的整体因果为**推断**。

## 3. 文字（字形栅格化与缩放）/ Text (glyph rasterization & scaling)

- **字形栅格化**：BLF（Blender Font 库）基于 FreeType；字号换算成 26.6 定点数（×64 后取整），即字号实际量化到 1/64 像素步长，最小 1px；DPI 用固定常量传入栅格化器。**确证（来源10）**。
- **字形缓存（glyph cache）**：按「字号 + 粗体/斜体 + 可变字体参数」键控整套缓存，单个字形再按「字符码 + 横向亚像素偏移档位」键控；任一参数变化即重建。亚像素定位在小字号最多提供 4 个横向档位、大字号减少、超大文字跳过。**确证（来源9）**。含义：横向分数位置不靠移动整张位图（会糊），而是从不同亚像素相位的栅格化结果里选——字形不会因分数坐标而蠕动。
- **抗锯齿与 hinting**：灰度覆盖率渲染 + 约 1.43 的 gamma 查找表做感知校正；默认「轻 hinting」（只约束垂直方向），小字号下步进取整到整像素，避免字符间距抖动。**确证（来源9）**。
- **缩放行为**：BLF 有两条路——按新字号重栅格化（触发缓存重建），或对已有字形位图做矩阵纵横比缩放（aspect scaling，不重栅格化，位图被拉伸）。**确证（来源10）**。节点编辑器文字随视图缩放时的轻微发糊与「矩阵拉伸位图」一致；要清晰就要么按档位字号重栅格化、要么像素对齐。**推断**。
- **像素对齐**：节点原点取整的直接动机就是「文字内容永远像素对齐」——文字锚点与框共用同一整像素原点，字形再按整数基线偏移摆放。**确证（来源8）**。
- **图标同理**：UI 图标是内嵌 SVG，按「请求的位图尺寸」首次使用时栅格化并存进同一套字形缓存，即按尺寸重栅格化（矢量→位图），官方称可在任意尺寸最优显示；设计规范要求图标特征对齐 100 单位网格、最小特征 1 格。**确证（来源2）**。

## 4. 连线（noodle）：采样、光栅化、端点锚定 / Wires (noodles)

- **解析贝塞尔 + GPU 逐顶点求值**：每条连线以四个贝塞尔控制点作为实例数据，顶点着色器沿参数 t 求值三次贝塞尔曲线并计算切线，在切线空间把顶点沿法线方向展开成条带——不是 CPU 预采样折线。每个实例同时含「轮廓层 + 主芯层」两层（主芯约为轮廓宽的六成多），一笔画出带描边的粗线。**确证（来源11）**。
- **宽度与缩放的关系**：展开方向经过与中心线相同的模型-视图-投影线性部分再乘纵横比修正，因此线宽随缩放同比变化、各向同性。**确证（来源11）**。
- **抗锯齿**：片元阶段用「中心线距离场 + 平滑阶梯过渡函数」做边缘羽化，羽化宽度为固定的小数单位（约 0.75 线宽单位）；虚线的每个 dash 端头也做同款羽化。**确证（来源11）**。即：noodle 的 AA 也是解析覆盖率混合，不是 MSAA。
- **端点不脱开**：贝塞尔首尾控制点就是插座的运行时位置，而插座位置每帧由节点边界重算并与节点原点同一相位取整（防抖动注释）；端点与框因此不可能脱开。**确证（来源8、11）**。
- **辅助路径**：拖动中的临时连线开「线平滑」（line smoothing）绘制；区域/分区（zone）轮廓线走通用折线着色器——该着色器把线段展开为**屏幕空间固定像素宽**的条带（宽度乘像素尺寸系数），线平滑开启时左右各加 1px 线性覆盖率羽化。**确证（来源8、12）**。同一仓库里两种宽度语义并存（noodle 随缩放变粗、轮廓线屏幕定宽），说明宽度语义是按元素可选的，关键是每种元素内部自洽。

## 5. 平移/缩放：为什么全画面不互相爬 / Pan & zoom — why nothing crawls

- **单一变换、单一相位**：全区域共用一次 View2D 映射 / 同一 MVP；所有元素在进入该变换之前（或转换出绘制坐标时）做同规则整像素取整。相同帧输入产生相同光栅结果，闪烁只可能来自「逐帧变化的采样相位」而非重绘本身。**确证（来源5、11）** + **推断**（因果总结，呼应来源14）。
- **相机不量化、元素量化**：可见视图矩形保持浮点（拖动平移也不取整），所以运动是连续的；但节点原点/插座的整像素取整让内容整体以 1px 步进锁步平移。**确证（来源5、6、8）**。
- **滚轮缩放锚点**：开启「缩放到鼠标」时，先算鼠标在可见矩形内的分数偏移，缩放后反向平移视图使该点在屏幕上不动；仅当缩放结果落在允许的缩放上下限内才应用锚定。滚轮是固定比例步进（默认步进比例约 0.0375），另有拖拽式连续缩放模式。**确证（来源6）**。
- **滚动条量化**：拖动滚动条时，位移按「每个像素对应的视图尺寸」量化后乘回，官方动机就是避免可见的 UI 抖动；而平移拖拽不做此量化（因为元素相位已锁步）。**确证（来源6）**。这是「相机量化」策略在 Blender 里的显式存在形态：**在无法保证相位一致的交互（滚动条）上量化，在相位一致的交互（画布拖拽）上不量化**。
- **网格不呼吸的机制**（对照本仓「网格整数格」）：Blender 点阵网格的稳定性不来自「世界坐标整数格」，而来自像素相位管理——按缩放档位（对数底 5 的层级）选间距，点的绘制尺寸向上取整到整像素并对齐半像素中心，透明度按理想/钳制尺寸之比的平方补偿使亮度均匀，最细档渐隐避免 pop-in。**确证（来源5）**。启示：网格线/点必须与相机量化共享同一相位（例如取整后的相机原点 + 整数格间距），否则网格会逐线呼吸。

## 6. 重绘策略 / Redraw strategy

- **每帧重建绘制数据**：界面绘制以立即模式/批为主，官方文档明言立即模式缓冲不做缓存、性能靠批量；widget 把填充、描边、浮雕、小图标合为「每 widget 一次绘制」并可多 widget 实例化。**确证（来源1、7）**。
- **无脏区合成**：区域按事件/通知标记重绘，交互期间是整区域连续重绘；绘制数据逐帧重建。UI 层没有「静态内容位图缓存 + 脏矩形」机制（3D 视口的 draw manager 有「录制一次、提交多次」的命令缓存，但那是场景绘制，不是 2D UI）。**推断（基于来源1、3的架构）** + **确证（来源3）**。
- **静态内容每帧重光栅化会不会闪？不会**——只要变换相位确定，逐帧重绘的输出是逐位相同的；闪烁的充分条件是采样相位/取整相位逐帧变化。**推断（基于来源14的采样相位原理）**。因此「每帧全量重画」不是问题，「每帧相位不同」才是。
- **UE 对照**：Slate/UMG 一侧提供 InvalidationBox 显式缓存子树、避免逐 widget 逐帧重绘（需手动失效），与 Blender 的「全量重建但相位确定」是两种哲学。**确证（来源17）**。

## 7. 低缩放 LOD 与档位策略 / Low-zoom LOD & tiers

- **节点细节 LOD**：视图缩放低于阈值（约 0.2 倍，再乘 UI 缩放系数）时跳过标签、插座等细节。**确证（来源8）**。
- **网格 LOD**：点阵网格按对数缩放档位（每档间距 ×5）逐档显示，点大小钳制 + 整像素对齐 + 亮度补偿，最细档渐隐防 pop-in——「档位 + 淡入淡出」而不是连续缩放到底。**确证（来源5）**。
- **文字/图标档位**：没有官方「缩放只在档位绘制」的成文规则，但机制上等价——字形按字号键控缓存、字号量化到 1/64 px，图标按请求尺寸重栅格化；非整数缩放若走位图矩阵拉伸就会糊（**确证（来源2、9、10）**，档位化建议为**推断**）。
- **对 MC 的建议形态**：位图字体/图标在低缩放下隐藏或换简化版（对齐 Blender 的节点 LOD），缩放只在整数档位（1x/2x/0.5x…）重栅格化，档位之间宁可淡出也不要分数拉伸。**推断**。

## 8. UE Slate / Blueprint 图编辑器对照 / UE Slate comparison

1. **几何与变换**：Slate 的 FGeometry 携带局部尺寸与累积渲染变换，所有子部件经同一几何链变换——与 Blender「单一共享变换」同构；像素对齐是 UMG 的常见优化主题。**推断**（UE 官方文档页为 JS 渲染，本次未能抓取正文；机制描述基于公开常识，不标注确证）。
2. **缓存策略双轨**：RetainerBox 把子控件渲到 Render Texture 再进材质（整组一次绘制 + 可做特效），InvalidationBox 缓存子树并要求显式失效——UE 用「缓存 + 显式失效」换取少重绘，代价是要管理失效时机。**确证（来源15、17）**。
3. **离散缩放档位**：UMG 的 DPI 曲线默认连续，但官方/社区推荐用自定义曲线强制离散档位（如 1.0/1.5/2.0），避免 UI 落在分数缩放导致文字与贴图发糊；并建议按最低分辨率设计、源图高分辨率 + mipmap。**确证（来源16）**。「蓝图图编辑器文字像素对齐、图缩放离散档位」的具体实现本次未取得可引来源——**推断**，不作结论。
