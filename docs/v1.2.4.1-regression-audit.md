## ✅ 已修复

### 1. 雷达红石输出失效（高危）— `RadarBlockEntity.java:557`

**提交**：9c46fb9
**根因**：`tick()` 运行分支 `evaluator.evaluate()` 后，`rs.writeOutputs(results)` 被误删（注释重写时删掉），`results` 成为死变量。`broadcastEvalSnapshot()` 只发客户端 DEBUG_PROBE 包，`RedstoneLinkHelper.writeOutputs` 是唯一调用 `REDSTONE_LINK_NETWORK_HANDLER.updateNetworkOf` 写红石网络的路径 → **雷达所有 REDSTONE_OUT 输出失效**（信号恒为 0/陈旧），Sable/非 Sable 雷达均受影响。
**修复**：在 `setRadarPos(null)` 之后恢复 `rs.writeOutputs(results);`（与 Sensor/Blueprint/ProgramComputer/Monitor/ControlSeat 一致）。

> ⚠️ 雷达机制提醒：雷达锁定通过客户端射线检测**空中 blip 小方块**（`RadarLockHandler.findBlipClient`，坐标变换与渲染器一致，2.0 容差）。blip 不是真实方块、无 `getBlockEntity` 可查。**服务端锁定路径（`toggleLock`）不得加"目标实体必须存在 / 目标位置必须有方块"的检查**，否则空中选中直接失效。

## 🔴 已修复：高危

### 2. 传感器错误引用任意子关卡姿态（中-高危）— `SensorBlockEntity.java:183`

**提交**：9c46fb9
**根因**：旧代码 `Class.forName("dev.ryanhcode.sable.api.sublevel.SubLevel")` 类名错误（jar 里不存在），反射一直死，`getSublevelOrientation()` 恒返回 null（传感器报告自身朝向）。9c46fb9 改走 `SableReflection` 后路径复活，但 **`getLogicalPose(allSubs.get(0))` 无成员检查**——取容器列表里第一个子关卡的姿态，套用到任何传感器上。
**症状**：单机/LAN（dist=CLIENT）下，放置在地面上（不在结构上）的传感器，会把**任意一个已加载子关卡**的姿态当作自己的姿态 → `attitudePitch/Roll/forwardYaw/forwardPitch` 图输入被远处结构污染，破坏依赖姿态的自动化。
**修复（2026-07-31）**：`getSublevelOrientation(level, worldPosition)` 传入传感器自身坐标，遍历子关卡做成员检查——仅当 `sl.getBlockEntity(worldPosition) != null`（传感器确实位于该子关卡内）才应用其姿态；不在任何子关卡返回 null（保持自身朝向）。

## 🟠 已修复：中危

### 3. 子图 flipflop 同步风暴 — `BlueprintBlockEntity.java:74` / `ProgramComputerBlockEntity.java:70`

**提交**：c06c320
**根因**：`changed` 判断从"顶层 flipflop 状态 diff"改成"顶层 diff **或** 任一子图 flipflopStates 非空"。`lastSyncedFlipflopStates` 只记录顶层 map，子图 flipflop 无基线对照 → **只要封装子图内有 LATCH/GATE/T_FLIPFLOP/LOOP/FUSE 节点（含恒 false 的），`changed` 永远为 true**。
**症状**：`RuntimeStateSyncPacket` 每 tick（20/s）广播给区块内所有玩家，永不收敛；客户端每包在主线程 clear+rebuild flipflopStates/subStates。多个块 = 网络风暴 + CPU/GC 抖动。
**修复（2026-07-31）**：新增 `lastSyncedSubFlipflopStates` 基线字段，子图 flipflop 也做 diff 而非存在性判断；子图全部消失（封装删除）时也触发一次通知客户端清空。顶层与子图都不变则不再广播。

### 4. SableReflection 专用服务器硬禁用 — `SableReflection.java:141`

**提交**：9c46fb9
**根因**：`if (FMLEnvironment.dist.isDedicatedServer()) { available = false; return; }`。注释称"Pose3dc 等引用 ClientLevel"——**事实错误**（javap 验证 bundled jar 中反射链全部服务端安全）。旧代码无此守卫，专用服务器上反射可正常工作。
**症状**：专用服务器 + Sable：`SablePacketHelper.scanDevices` 恒返回空列表 → 便携终端无线设备列表显示 0 台。
**已排除的子场景**：`BlueprintTogglePacket` 的 isSable=true 分支当前不可达（所有 7 个发送点都用 2-arg 构造）。
**修复（2026-07-31）**：移除 `isDedicatedServer()` 早退。各阶段 best-effort 加载保证可选类缺失时安全降级为 null。

## 🟡 已修复：低危

### 5. subStates 全量快照恢复 → 状态泄漏入 NBT — `SyncedGraphBlockEntity.java:383`

**提交**：c06c320
**根因**：`recompileEvaluatorFull` 对 `runtimeState.subStates` 全量快照/全量 `putAll` 恢复，无"现存 ENCAPSULATION 节点"过滤；全库无任何清理已删封装 subStates 的路径。
**症状**：删除封装节点后其 DELAY 队列/flipflop/PID 状态永久残留 → 序列化进 chunk NBT 每次存档、跨 reload 存活；且节点 ID 复用（新蓝图 encap 撞旧 ID）时经 `restoreSubState` 继承旧状态，污染实时计算。同时也让 #3 的广播风暴在删除 flipflop 节点后仍持续。
**修复（2026-07-31）**：`recompileEvaluatorFull` 恢复前按当前 `graph` 的 ENCAPSULATION 节点 ID 过滤 subStates（剪除已删除封装）；`loadGraphFromBytes` 成功替换图后清空 `runtimeState.subStates` 与 `flipflopStates`，避免旧图状态跨加载泄漏。

### 6. RuntimeStateSyncPacket 线格式变化 — `RuntimeStateSyncPacket.java:27`

**提交**：c06c320
**根因**：clientbound 包追加第三个字段 `subFlipflopStates`，但 mod 版本号未变（仍 1.2.4.1）。
**症状**：旧客户端连新服务器：旧 codec 只读 pos+flipflopStates → `PacketDecoder` 检测到剩余字节 → IOException → **玩家被踢下线**；反方向同理（buffer underrun）。
**结论（2026-07-31）**：**无需代码改动**。已确认 NeoForge 通道版本 = mod 版本字符串，`1.2.4`（已发布 tag）vs `1.2.4.1`（当前）字符串不同 → 混连时**通道握手友好失败**（版本不匹配提示），不会静默解码崩溃。线格式变更已含在 1.2.4.1 版本号变更内，发布 1.2.4.1 即天然隔离 1.2.4 客户端。若未来在**同版本号内**改线格式才需 bump 或兼容 codec。

## 附录：总线专项修复（2026-07-31）

用户报告 "BUS_OUT 写入但 BUS_IN 收到 0"，27 路验证定位 5 根因，已修 4：

1. **WIP stale-owner cleanup 错杀活 owner**（`BusChannelHelper`）— **已回退**（方案 A）。WIP 在注册失败时只查本图同名，无 liveness 检查即强杀其他 block 的活频道 → 所有权翻转，被夺方写脱离频道的 map。回退恢复"首个注册者获胜"。WIP 原始目标（过时 owner 残留）由 `recoverConflictedChannels` 覆盖。
2. **`recoverConflictedChannels` 增强 liveness**（`BusChannelHelper`）— owner chunk 加载时检查该处是否仍有 `GraphBlockEntity`；BE 消失（残留）用 40-tick 短超时回收，为 Sable 坐标瞬时不可解析留缓冲。
3. **`loadGraphFromBytes` 补 generation bump**（`SyncedGraphBlockEntity`/`Blueprint`/`Monitor`/`Radar` 四处）— `NodeGraph.load` 产生 generation=0 的新图，可能等于 `lastGraphGeneration` 导致 `graphChanged()` false → 重注册被跳过，新图 BUS_OUT 永不注册。
4. **跨 block BUS_IN band**（`GraphEvaluator`/`OpExecutor`）— `BusBandUploadPacket` 只更新发送者方块的服务端图，其他 block 的 BUS_IN 持有过时/空 `signalBands`。修复：求值器 KEY 查询优先读全局 `BAND_REGISTRY` 权威定义；`ADD_NODE` 创建 BUS_IN 时若频道已有定义则初始化 `signalBands`。

WIP 文件已还原：`GraphEditor`、`RadarLockPacket`（恢复编辑会话校验）。
